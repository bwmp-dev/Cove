# Cove

Cove is a custom, lightweight deployment control plane, not a wrapper around another hosting panel.

## Agreed design

- Exactly one main node hosts the dashboard, API, PostgreSQL configuration database, and durable job queue.
- Worker nodes run Docker/Compose workloads. There is no artificial node limit; capacity depends on control-plane resources.
- The main node initiates SSH connections to workers. Workers need no public management API. Private networks, VPNs, and eventually jump hosts can provide reachability.
- Each worker uses a small Go executable with structured requests and responses. Long-running operations must persist locally and survive SSH disconnection. Reconnection reconciles operation IDs before retrying.
- The main node can also host workloads using the same executable through a local transport, without SSH to itself.
- Add node generates an expiring one-time setup command. Bootstrap uses HTTPS, installs prerequisites, configures a dedicated SSH identity, registers the host key, and verifies connectivity from the main node.
- Enrollment and readiness are distinct states. Existing Docker installations, workloads, and unrelated SSH configuration must be preserved.
- Workloads have explicit node placement. Compose stacks stay on one node. Cross-node networking is explicit.
- Public workers handle ingress/TLS locally; application traffic need not pass through the main node.
- Applications continue running when the control plane is offline.
- Projects, environments, workloads, releases, operations, routes, storage, and backup policies form the domain model.
- Secrets are encrypted at rest and delivered only where needed. Per-node SSH credentials and pinned host keys are mandatory.
- Builds, backups, and other expensive operations run on workers. Logs and telemetry are bounded.

## Delivery order

1. Persistent node enrollment, generated setup command, worker installation, SSH verification, and capability probe.
2. Compose deployment with durable worker operations, per-workload locking, logs, and interruption recovery.
3. Dashboard, projects/environments, Git automation, local workloads, and routing.
4. Database and volume backups, tested restores, dedicated build nodes, and Coolify migration.

Workers target Linux amd64/arm64 with systemd and OpenSSH; automatic installers cover Ubuntu/Debian and supported EL distributions. Single-hop bastions use independently pinned SSH identities. A node with Docker access is a privileged infrastructure identity even when its SSH command is restricted.

## Implemented release scope

Individual email/password and GitHub OAuth accounts, optional open registration, verified email changes, password resets, invitations, teams, shared-worker assignment, and project/environment permission grants are implemented. Existing resources and the administrator migrate into a default team. Instance administration is separate from team ownership; API authorization scopes configuration, operations, logs, backups, tokens and audit records. Shared workers do not isolate hostile tenants: Docker/Compose access can compromise other workloads on the host, so mutually untrusted teams need separate workers or VMs.

Account acceptance covers legacy database/session migration, invitation expiry/replay/revocation, account disablement, password/session revocation, scoped resource isolation, token permission revalidation, and GitHub state/cookie/PKCE, verified-email, collision and linking checks against a controlled provider. Linux race tests and PostgreSQL integration pass. Packaged Chromium verifies invitation signup, team switching, environment-scoped viewer access, denied resource access, account disabling and password rotation alongside the real worker resource lifecycle. Actual GitHub and SMTP credentials must be configured and tested on each deployment; local provider/mail fixtures do not establish external delivery or provider acceptance.

Implemented: persistent enrollment, restricted SSH RPC, pinned host identities, local socket transport, browser sessions and password rotation, workload-scoped expiring/revocable API tokens, encrypted workload configuration with per-key secret updates, durable operations and cancellation, Compose services and one-shot jobs, Git checkouts, retained-image release rollback, bounded/redacted logs, periodic node checks, mutation audit records, and self-hosted packaging. The React/TanStack frontend supports these management workflows. Worker upgrades drain active operations, retain queued work across restarts, and restore the previous executable if replacement readiness fails. Writable Git-release bind mounts are rejected in favor of named volumes or stable host paths.

Verified locally: PostgreSQL enrollment/session integration, password rotation/session revocation, scoped-token isolation/revocation, per-key secret preservation, and panel backup/restore; real Docker/SSH deployments, rollback, cancellation, restart/replay, stop operations, and successful/failing jobs. Packaged Chromium tests cover authentication, enrollment, responsive node lists, deployment, live container state, rollback, token creation/revocation, and password rotation. A dedicated Ubuntu 24.04 QEMU VM passed generated installation, pinned SSH enrollment, local-socket deployment, application survival during upgrade, reenrollment, replacement readiness, and restoration after an intentionally broken replacement. These are local test-TLS checks, not public certificate or private Git-provider acceptance.

Projects and environments, signed GitHub push webhooks with durable deduplication and commit pinning, managed Traefik application ingress, local and S3 encrypted storage backups, scheduled backups, verified restores, audit browsing, release retention, safe workload/node deletion, and enrollment expiry are implemented. The optional local-worker Compose service shares the panel's HTTPS ingress through a protected Unix socket. Authenticated mutations and rejected authorization checks are audited without request bodies or credentials. Ten recent releases are retained, plus releases referenced by the current deployment or backup records; pruning only removes Cove-owned release images and source directories.

Linux acceptance covers Ubuntu 24.04 amd64 in an isolated QEMU VM: generated installation, successful upgrade, failed replacement recovery, private HTTPS Git authentication and pinned builds, rollback with the Git server unavailable, packaged main-node execution, shared dashboard/application TLS, and application survival during control-plane outages. Pebble acceptance exercises actual ACME challenges, trusted certificates, automatic renewal, proxy restart and CA outage. PostgreSQL volume backup/restore is tested with local storage and an encrypted S3 repository over verified TLS. Restore checks recover database contents, remove files created after the snapshot, retain a safety snapshot, and enforce retention. ARM64 worker unit tests pass under emulation; ARM64 systemd installation and other distributions are not runtime-certified.

Packaged Chromium acceptance includes project/environment assignment, masked backup-policy editing, deletion refusal for running workloads, stopped-workload deletion and pending-node deletion. Responsive screenshots cover 390, 768 and 1440 pixel widths. Inventory integration covers 2,048 synthetic nodes and workloads with 40 list reads from 20 concurrent clients; this is not a fleet-capacity benchmark. Worker execution and dispatcher concurrency remain bounded rather than growing with inventory size.

Deployment acceptance still requires the target site's DNS, firewall, SSH reachability and publicly trusted certificate issuance. Isolated ACME tests cannot prove those external conditions. No existing Coolify applications were migrated or modified. Dedicated build nodes, cross-node scheduling, jump hosts and automatic Coolify import are outside this release scope.

Live acceptance on an authorized Ubuntu amd64 VPS pair covered dashboard and worker installation, pinned SSH enrollment, public TLS issuance, login/session protections, remote deployment, persistent-volume backup and exact restore, and application survival during worker and dashboard restarts. Private host identifiers and operational recovery records are maintained outside this repository.

Traefik-specific acceptance covers automatic ACME renewal, certificate persistence, dynamic removal/restoration of the last application route, shared-panel continuity and management API isolation. Public TLS and remote deployments passed again after migration. Other hosts and platforms require their own deployment acceptance.

Workload release rollback restores saved Compose configuration and retained local images; it does not reverse application data or database migrations. Backups stop the workload for consistency and reject storage shared with other running containers. Restore requires the current storage layout, creates a safety snapshot and leaves the workload stopped if recovery fails. Local backups do not protect against node loss; offsite backup passwords and the panel encryption key must be backed up independently. Cancellation stops the command and leaves already-applied container changes for inspection. Operation journals are retained for reconciliation and investigation; audit history follows configured retention caps. Per-operation output and telemetry history are bounded, but operation history and worker journals use age/count retention with explicit exemptions for unfinished and referenced recovery/release/backup records.

Environment previews copy one production environment per branch name across selected repositories: matching branches build, everything else runs the production state pinned at creation, data is copied once from read-only sources into preview-owned storage, connections are recreated between the copies, and protected routes are published after every resource is healthy. See DEVELOPMENT.md for the exact semantics and limits.

Private connections are explicit, directional TCP grants from one source service to one target service port, enforced on workers by a per-node link gateway with dedicated internal networks per source hostname and per target, and pinned mutual TLS between workers. They do not replace or restrict shared networks, published ports or public routes. See DEVELOPMENT.md for the operating model and limits.

Notification channels reuse encrypted team infrastructure connections and durable operation/health delivery queues. Channels can select exact catalogue events, including backup/restore/drill outcomes, or retain legacy success/failure/health selection. SMTP channels reuse the instance mailer; generic webhooks support timestamped HMAC signatures. Telegram, ntfy, Gotify, Pushover, Matrix and Teams use the same bounded dispatch concurrency and retry limit. PagerDuty/Opsgenie require matching alert/recovery routes with stable incident keys and ordered delivery. Workload owners are current team members and convey no extra access; owner email routing requires a verified, enabled account. Node CPU, used-memory and data-filesystem disk threshold rules persist confirmation/repeat/recovery state and restrict delivery to selected channels, with at most 100 rules per team and 32 channels per rule. The evaluator accepts fresh worker samples independently of storage and shares those measurements with metric collection. Certificate-expiry and container restart/OOM/crash rules use sanitized workload-scoped worker observations, with intentional-operation/manual-stop and one-shot-job suppression. Managed ACME key material remains on the worker. Historical operation notifications remain subject to the historical-storage limitation above.

Telemetry persists bounded node/container snapshots in minute/hour/day tiers and redacted workload log entries with incremental cursors, replay deduplication, filters and page downloads. Instance administrators configure global metric/log age, row and accounted-byte caps and audit age/row retention; usage distinguishes logical accounting from physical PostgreSQL allocation. Collection and results are bounded, and missing samples and log gaps remain explicit. Operation retention coordinates worker journal acknowledgements with panel deletion while preserving reconciliation and retained references. Mount capacity reporting and scheduled cleanup use bounded previews, ownership/reference checks and explicit volume/non-Cove opt-ins. Merged live tails retain container identity and redaction. Advisory deployment capacity checks compare declared limits with measured free resources, historical sizing suggestions require enough recent samples, and configured node prices roll up by explicit equal-resource allocation without currency conversion. Opt-in managed proxy access logs provide bounded sanitized route traffic, and panel HTTPS checks feed uptime alert rules and opt-in public project status. Sealed log forwarding outboxes use bounded retries/retention, while a separately token-protected Prometheus export exposes fresh instance metrics. Network collectors run independently of deployment dispatch.

Backup locations additionally support native Backblaze B2 through the existing encrypted rclone repository transport. Calendar retention adds bounded daily, ISO-week and monthly snapshot tiers to keep-last, with explicit worker capability checks before applying deletion. Stopped-volume and PostgreSQL/MariaDB logical backups retain their existing paths. MongoDB replica-set archives and Redis/Valkey RDB snapshots stream directly from the live container into a separate encrypted restic data snapshot. A linked metadata snapshot captures the release; both are pruned together with replay-safe deletion. Publication requires a successful isolated restore using the source image, with a 2 GiB verification memory limit. A per-resource journal reconciles interrupted snapshot creation, and two private per-resource staging directories bound each dump to 64 GiB. Restore drills and isolated resource copies understand the linked snapshots. In-place restores validate first, retain a safety snapshot, journal the original running set, and leave failed restores stopped for explicit recovery. MongoDB in-place restore requires a standalone target or writable single-member replica set; multi-member backups can restore into a separate single-member resource. Redis/Valkey restores require standard `/data` persistence paths and regenerate append-only files from the verified RDB. Permission-gated, audited downloads stream database dumps or volume tar archives through restricted SSH without buffering on the panel. Raw uploads and configured S3 object imports are size-bounded and restored in isolation before becoming encrypted backup records; importing never overwrites the running source. A worker-wide transfer journal and ownership-scoped helper labels clean plaintext and interrupted helpers on restart. Host snapshot plugins and PITR use separate host recovery paths.

Panel self-backup and exact snapshot recovery run through a root host timer, while the panel remains a non-root container without Docker access. Administrator settings seal offsite credentials and independent encryption passwords; host-only signed requests receive opaque plans, opened through a restricted local CLI. Encrypted snapshots include the PostgreSQL dump, actual runtime credentials, installation Compose/Traefik files, certificates and immutable installation image IDs. Publication requires an isolated database restore, and retention bounds local/offsite history while preserving active recovery references. Pre-update snapshots are mandatory before image replacement; historical panels without the new API use an authenticated, non-secret local bootstrap plan. Recovery validates artifacts before stopping the panel, retains a fresh safety snapshot, restores matching database/images/configuration, cancels restored unfinished intents and pins previews for review. A private host journal resumes interrupted restores without requiring the panel to be running. Updates pause after recovery until an explicit review/resume. Host-loss recovery, cross-major PostgreSQL conversion, filesystem permissions and real offsite/provider behavior still require separately coordinated acceptance.

Optional filesystem-backed volume backups inspect the host mount namespace and use read-only Btrfs subvolume, ZFS dataset or traditional LVM snapshots. Containers pause only for snapshot creation and resume before encrypted repository copying; original mount identities remain in restore metadata. Unsupported layouts fall back to the existing stopped method before any snapshot mutation. Failures after creation fail the backup, and LVM validity is checked before publication. A private bounded journal and ownership-tagged resources coordinate cleanup with worker restart and a host systemd lease reaper. The panel receives only sanitized mount capabilities and backup-method results; host tools and kernel modules remain host prerequisites.

Resource-editor file browsing uses structured restricted RPC for running containers and attached Cove-owned volumes, with team/project/environment authorization, ownership checks, clean-path/symlink restrictions, bounded data, revision checks and action audits. The 32 KiB editor is independent of administrator-bounded binary streams, which check size/digest without buffering file bodies on the panel. File contents are ephemeral and non-cacheable; volume changes require stopped users and all access coordinates with worker operations/draining. Existing-file edits preserve inode metadata and are not durable deployment operations. Host package/firewall/provider changes and resumable workload moves use separate increments.

Optional single-hop SSH bastions have separately pinned host keys and independently sealed forwarding identities. Forwarding does not relax worker forced-command keys, and both hops authenticate before restricted RPC or raw transfer. Authentication-key rotation stages a second restricted key, proves a fresh connection, commits the panel identity and only then removes the old key. One sealed pending/last result per node and one bounded worker journal/staging file make lost receipts and restart recovery explicit. Confirmed host-key changes refuse connections and feed assigned-team alert routing; ordinary network errors do not clear them. Operators configure the dedicated bastion account's forwarding restrictions outside Cove.

PostgreSQL point-in-time recovery uses a separate WAL-G archive in the resource's selected storage, encrypted with an independent sealed key. A bounded worker helper streams a physical replication slot through a private mounted Unix socket and an authenticated local rclone S3 bridge; the panel gains no Docker privileges. Enabling/disabling the socket requires a PostgreSQL restart, while subsequent base backups and WAL capture stay online. Base images and operation references remain protected. Per-resource age/count/byte/object bounds, a checkpoint-enforced source slot budget and ownership markers prevent unbounded retention or cross-resource deletion. Recovery windows require a complete archived transaction heartbeat and per-base WAL integrity checks. Restores always replay into fresh isolated storage, verify promotion and a normal administrator login, and publish an offline resource with new protected credentials and no public endpoints. Source data and authentication rules are preserved. Durable cleanup journals retain failed copy storage for inspection and remove only owned temporary helpers on restart.

## Completion requirement

The user explicitly requires a fully fleshed-out, production-ready product, not a proof of concept. The delivery order above describes implementation increments, not acceptable stopping points. Release acceptance must cover authenticated dashboard workflows, durable execution and recovery, secret handling, Git/build deployment, routing, backup/restore, installation/upgrades, and real Linux validation. Unverified production behavior must remain explicitly identified.

Host security maintenance uses allowlisted worker RPC and a bounded trusted host helper for cached package/security/reboot inspection. An explicitly confirmed Cove-owned native timer delegates security updates to the host package manager without changing unrelated schedules or expanding panel privileges. Host state is limited to a fixed owner marker, service/timer pair and two bounded staging claims.

Node firewall changes use an owner-scoped nftables application-port table, management-port exclusion, revision-bound preview, an independent native timed revert and a fresh panel-to-worker connectivity check before confirmation. A protected boot service restores committed policies and excludes new management listeners; external tables remain untouched. The native recovery executable and single preimage journal are bounded independently of operation history.

Cloud server provisioning seals provider tokens and queues a bounded durable job before an external create request. Hetzner, DigitalOcean and Vultr have fixed TLS API origins. Lost acknowledgements reconcile owned markers using reads; creation is never retried automatically. Automatic enrolment reuses the existing one-use installer token and pinned worker identity. Node removal and abandoned tracking never delete provider servers.

Team and environment resource defaults fill missing deployment limits while preserving Compose declarations and explicit per-service overrides. Capacity-based placement suggestions read fresh team-assigned node measurements and never choose or move a resource automatically.

Per-service GPU selection extends existing sealed resource limits and retained release configuration. Explicit native inspection reports bounded NVIDIA/CDI identities; the worker revalidates selected devices and Docker driver availability before deployment. No device credential, host driver installation, implicit all-GPU allocation or additional persistent inventory store is introduced.
