# Development

## Releases and updates

GitHub Actions tests pull requests and builds Linux amd64/arm64 dashboard and worker images. Every successful push to `main` publishes `ghcr.io/bwmp-dev/cove:beta` and `ghcr.io/bwmp-dev/cove-worker:beta`, plus immutable `beta-<full commit>` tags. Release Please opens version/changelog PRs from conventional commits. Merging a release PR creates the versioned GitHub release and publishes `:vX.Y.Z` and `:release` images in the same workflow; manually pushed tags do not publish stable builds. Newly created GHCR packages must be made public in their package settings before anonymous hosts can pull them. Release Please uses the repository GITHUB_TOKEN and needs permission to create pull requests; publication does not depend on a separate tag-triggered workflow.

On a Linux panel host with this checkout's Compose files and Python 3, update with `sudo python3 scripts/update-panel.py vX.Y.Z --installation /opt/cove`. For the optional local container worker, keep using the installation's `COMPOSE_FILE=compose.yaml:compose.local.yaml` configuration. The updater pulls and pins image IDs, saves a private resolved Compose configuration, environment and database dump in `.cove-updates/`, drains the local worker, replaces only Cove services, and waits for panel health and local-worker readiness. On failure it restores previous images. Database/schema changes are not automatically reversed. Back up the encryption key independently. A successful update saves `COVE_VERSION` in `.env` for subsequent Compose commands; avoid overriding it in the shell. Keep private recovery files off public storage.

New systemd node enrollments install `cove-worker-update.timer`. Every two to three minutes, nodes compare their binary with the worker bundled in their panel, download it over HTTPS, verify its SHA-256, drain active operations, replace the binary and check readiness. Failed readiness restores the previous binary. Application containers keep running. Stopped workers and workers already in maintenance are left alone. Nodes follow their panel, including a panel rollback; they do not independently fetch the newest GitHub release.

Existing systemd nodes need a one-time installation: renew their enrollment in Cove and run the generated setup command after updating the panel. This preserves the node identity and installs the timer. A systemd local worker also needs this enrollment path. Inspect `systemctl status cove-worker-update.timer` and `journalctl -u cove-worker-update` on a node. Disable automatic worker updates with `sudo systemctl disable --now cove-worker-update.timer`. The root updater trusts only the configured panel HTTPS origin for executable releases; no enrollment or administrator token is persisted in it.

For unattended host updates, run `sudo sh scripts/install-auto-update.sh /opt/cove` once. Instance administrators select **Release** or **Beta** in Settings → Updates; the default is Release. The host checks hourly, reads the selected channel from the authenticated panel API, resolves its image label to an immutable version, then uses the same backup/drain/readiness/rollback flow. `sudo python3 scripts/update-panel.py --latest --channel beta --installation /opt/cove` overrides the saved channel for one check. Changing back to Release can downgrade the application; database/schema rollback remains manual. A channel without a published image leaves the installed version untouched. View `journalctl -u cove-panel-update`; disable with `sudo systemctl disable --now cove-panel-update.timer`. The updater is copied to `/usr/local/lib/cove/`; rerun the installer when the updater script itself changes. Backups accumulate intentionally; arrange encrypted off-host backups and prune old local recovery copies according to your retention policy.

Already-enrolled systemd workers can install just the updater without renewing enrollment: download `https://YOUR_PANEL/releases/worker/install.sh` to a temporary file over verified HTTPS, run it as root, then start `cove-worker-update.service`. This preserves SSH identity, enrollment and the worker's existing service configuration.

Requires Go 1.26.11+, PostgreSQL, and a Linux worker with systemd/OpenSSH. Worker binaries have no Go runtime dependency. The React/TanStack frontend lives in `frontend/`; use pnpm there. Production builds are served by Go from `frontend/dist`.

Build the control plane with `go build -o bin/cove ./cmd/cove`. Cross-compile `./cmd/cove-worker` with `GOOS=linux` and `GOARCH=amd64` / `arm64`, producing `bin/cove-worker-linux-amd64` and `bin/cove-worker-linux-arm64`.

Set these environment variables before starting the control plane:

- `DATABASE_URL`: PostgreSQL connection string.
- `COVE_ENCRYPTION_KEY`: base64-encoded 32 random bytes. Back this up independently of the database; losing it makes stored SSH identities unusable.
- `COVE_ADMIN_TOKEN`: at least 32 characters of cryptographically random administrator credentials.
- `COVE_ADMIN_PASSWORD`: optional legacy bootstrap password (16-72 bytes). Fresh installations omit it and create their administrator in the browser; existing password hashes are never overwritten.
- `COVE_PUBLIC_URL`: HTTPS origin reachable by workers, without a trailing slash or path.
- `COVE_BINARY_DIR`: compiled worker directory, default `bin`.
- `COVE_LISTEN`: default `127.0.0.1:8080`; put an HTTPS reverse proxy in front of it. Do not expose the plaintext API publicly.
- `COVE_FRONTEND_DIR`: defaults to `frontend/dist`.
- `COVE_LOCAL_SOCKET`: optional path to a separately running local worker's protected Unix socket. The control-plane user must have access to that socket. Local execution does not SSH to the main node.

The API initializes its schema on startup. Automation uses `Authorization: Bearer <administrator token>`. The browser uses an HttpOnly, Secure, SameSite=Strict session cookie after `POST /auth/login`; mutations require the configured origin. A PostgreSQL advisory lock permits only one dispatcher.

## Accounts and team access

Authentication APIs now expose TOTP enrolment/confirmation, one-time hashed recovery codes, passkey registration and passwordless sign-in, and multiple discovery-based OIDC providers. TOTP uses six-digit SHA-1 RFC 6238 codes with a 30-second period and one-step clock tolerance; accepted time steps cannot be replayed. Provisioning URIs and recovery codes appear only in their creation responses. Existing encrypted-secret storage protects TOTP seeds and OIDC client secrets. Enrolment revokes other browser sessions. Password and GitHub/OIDC sessions with an enrolled factor cannot use authenticated APIs until a second-factor challenge succeeds; passkeys require user verification and satisfy the second factor. `/auth/sign-in-methods` exposes provider buttons and, only for a live first-factor challenge within ten minutes, `second_factor_methods` (`totp`, `recovery_code`, `passkey`). `/api/account/sign-in-methods` exposes enrolment policy and `recovery_codes_remaining`. Regenerate recovery codes at `POST /api/account/recovery-codes` with `current_password` or a single-use TOTP/recovery `code`; the old set is atomically invalidated. An empty proof body is also accepted for a factor-verified session established within ten minutes (including fresh passkey sign-in). Remove TOTP at `DELETE /api/account/totp` with the same proof, then enrol and confirm a replacement normally. Removal refuses to leave no factor when instance or any membership team policy requires one; retain a passkey when replacing TOTP under mandatory policy. Removal revokes other sessions and outstanding linking/registration flows. Team owners and instance administrators can require enrolment; unconfigured accounts retain access to account settings so they can enrol. The startup administrator bearer credential remains the recovery path for policy administration. Disabling password login allows an explicit `break_glass: true` password login for instance administrators only; enrolled second factors still apply.

OIDC callbacks require state/browser binding, nonce, S256 PKCE, issuer/audience/signature/expiry verification, and a verified email claim. A provider identity never links by matching an existing email: link explicitly from a signed-in account with its current password, or a sign-in less than ten minutes old for a passwordless account. Account creation via OIDC is independent of open registration. Providers that do not issue a verified email claim are rejected, including Entra configurations without that claim. OIDC configuration changes invalidate outstanding flows. Admin provider responses include `redirect_uri`, derived by the same helper used for token exchange. `GET /api/account/identities` lists linked OIDC and GitHub identities; `DELETE /api/account/identities/{provider}` requires password or TOTP/recovery proof and refuses the last usable sign-in method, accounting for disabled password login and unconfigured GitHub login. Unlinking revokes other sessions and outstanding linking/registration flows. GitHub sign-in with pending second factor redirects to `/login?authenticated=1`, matching OIDC. Passkey sign-in options contain `publicKey` without a mediation hint. Initial provider configuration is not a connectivity test; acceptance with each deployment's provider remains necessary.

Login history is bounded to 90 days and the latest 100 events per API response. Socket peer addresses are used; forwarding headers are not trusted. Deployments behind a shared reverse proxy therefore share the address bucket. Existing minute limits remain; ten rejected requests per account or fifty per source within fifteen minutes lock that bucket for fifteen minutes. Password reset requests also retain their existing email-specific limits. When SMTP is configured, successful sign-in from a previously unseen secure browser-device cookie attempts a notification; deleting browser cookies creates a new device. Email delivery failures are logged without credentials.

Team-defined roles use a fixed permission catalogue (`view`, `read_secrets`, `operate`, `edit_configuration`, `manage_backups`, `manage_members`) in the same team/project/environment grants as built-ins. Every custom role includes `view`. `/api/session` includes `permissions` for the active team from this catalogue. Team-scoped delegated member managers may read the role list and use existing member/invitation APIs; editing role definitions and managing owners/admins retain their existing restrictions. Owners/admins retain existing privileges. Legacy aggregate access levels are conservative: partial custom roles do not acquire implicit editor access in list filters and compound workflows. Restores and drills additionally require configuration-edit permission. Only owners can manage owners; delegated member managers cannot create or modify administrators. Roles referenced by members or live invitations cannot be deleted.

Instance administrators configure audit export at `/api/settings/audit-export`. Every newly persisted audit event atomically queues a sealed destination snapshot for each enabled sink. HTTPS webhooks reuse the public-address DNS/dial protections, refuse redirects, and sign the Unix timestamp, a dot and the exact JSON body using HMAC-SHA256 in `X-Cove-Signature: sha256=<hex>` with `X-Cove-Timestamp`; `X-Cove-Delivery` is a stable deduplication key. Syslog uses RFC 5424 messages with RFC 6587 octet-count framing over TCP or certificate-verified TLS. Successful socket writes are transport acceptance, not proof of collector persistence. Unacknowledged webhook deliveries and failed syslog writes retry durably with capped exponential backoff. Pending deliveries are not pruned; monitor database growth. Audit retention is configurable from 1 to 3650 days (default 365); queued event payloads survive retention. Export starts with new events, not a historical backfill.

### Directory membership and recovery

Instance administrators map GitHub, SCIM or LDAP groups to a Cove team and a built-in role (`owner`, `admin`, `member`, `viewer`, `operator`, `editor`) or a custom role ID belonging to that team. Multiple sources combine their grants; removing one source restores the original manual membership and retains grants from other sources. Managed memberships reject ordinary edits/removal, with an explicit owner promotion available for recovery. A mapping also prevents deleting its custom role. Every effective membership change is audited in the same transaction. Removing the last active owner retains that owner as a local membership and records a warning; assign another owner before attempting to remove that access. Disabling the last active owner through SCIM is refused with 409 instead.

Retain the host's `COVE_ADMIN_TOKEN` and encryption key independently of the identity provider. This credential can administer settings even if the bootstrap account is disabled. To recover from a directory outage or bad policy, use it from an address allowed by Panel access to disable SCIM or re-enable/correct an LDAP provider with its current version, then grant an active local operator team ownership. For an account blocked by SCIM, first detach provisioning at `DELETE /api/settings/scim/links/{user}` with `confirm:true`, then re-enable the user through the existing administrator Users API. Detaching preserves its Cove account, OIDC identity and current disabled state; it removes SCIM group grants. Manual disablement cannot be undone by a later SCIM activation. Existing administrator password `break_glass:true` login remains available when password login is disabled, and still requires enrolled second factors. Test recovery before relying on directory-only sign-in. Keep a separate usable sign-in method before unlinking an identity; LDAP identities use provider IDs `ldap:<id>` in the existing account identity endpoints.

### GitHub organisation teams

Administrators select mapping targets from `GET /api/settings/directory/teams`, which returns every team's ID/name without depending on explicit membership. The endpoint is instance-admin-only; normal member visibility is unchanged. Member provenance includes friendly directory names only for instance administrators. GitHub preview rows include the affected Cove user's display name/email for review; unlinked upstream users remain a count. Those profile labels are not copied into membership audit details.

`/api/settings/github-team-sync` manages up to eight sources, each with at most 100 team-slug mappings. An App source uses an existing organisation installation with **Members: read**; the installation token is restricted to that permission. An OAuth source belongs to the configuring administrator and their immutable linked GitHub ID. After saving it, that administrator explicitly reconnects GitHub with the account-linking flow (`POST /auth/github/start`, `link:true` and current password, or factor proof for a passwordless account). Only that linking flow requests `read:org`; ordinary sign-in keeps its existing scopes. Only an OAuth response that actually grants `read:org` can replace the sealed directory credential. Organisation SSO may require authorising that grant in GitHub. Tokens never appear in source reads or audit records.

Preview a source with its current `version`, then reconcile with that version, the returned `roster_hash` and `confirm:true`. A changed roster/version or active refresh returns 409 and requires another preview. Matching uses existing linked GitHub numeric IDs, never email or mutable login names; unmatched GitHub users are reported, not created. Enabled sources refresh every 15 minutes, checked by a one-minute dispatcher loop, and each linked user's successful sign-in refreshes that user's claims. Individual sign-ins do not postpone the full refresh. Disabling a source pauses automatic refresh; an administrator can still explicitly preview/apply it. Deleting a source removes only its managed grants. Every page of each mapped team's membership must succeed before applying anything; permission errors, rate limits, suspended/disconnected installations and unavailable or demoted OAuth owners retain all existing access. [GitHub's team membership API](https://docs.github.com/en/rest/teams/members) includes child-team members.

Organisation-consent linking returns to `/admin?github_team_sync=connected#github-team-sync`, `permission_required` or `error`. The destination is fixed, never caller-supplied. Browser-bound state pins the initiating live admin session; successful consent preserves its existing second-factor verification rather than issuing a fresh first-factor session. Revoking that session prevents completing consent. Invalid/unbound state uses the generic login failure. Ordinary GitHub sign-in redirects are unchanged.

### SCIM 2.0 provisioning

The SCIM base URL is `https://YOUR_PANEL/scim/v2`. Generate/rotate the instance token at `POST /api/settings/scim/token` with the reviewed settings `version` and `confirm:true`; it is returned once and sealed at rest. Rotation immediately rejects the previous token, including an authenticated write still in flight. Enable provisioning separately with `PUT /api/settings/scim`. SCIM accepts only this bearer token, never browser cookies or the host administrator credential. Panel IP restrictions also apply, so include the provisioning service's real source addresses when enabling an allowlist. Keep HTTPS end to end. Disabling SCIM pauses provisioning without removing memberships.

Users and Groups support GET/list, POST, PUT, PATCH and DELETE, `application/scim+json`, discovery, weak version ETags and `If-Match`. Lists use one-based `startIndex`, default `count=100`, a maximum of 200 and `count=0` for totals. Supported filter attributes are User `id`, `userName`, `externalId`, `displayName`, `name.givenName`, `name.familyName`, `active`, `emails.value`, and Group `id`, `externalId`, `displayName`, `members.value`; string operators are `eq`, `ne`, `co`, `sw`, `ew`, `pr`, with `and`, `or` and parentheses. Supported attribute projection includes complex subattributes and `excludedAttributes=members`. PATCH supports case-insensitive operation names, pathless attribute objects, complex subattributes and one `eq` multivalue selector such as `members[value eq "id"]`. User PATCH returns the updated resource; Group PATCH returns 204 unless an `attributes` projection was requested. Bulk operations, sorting, nested groups, password synchronization, arbitrary schema extensions and other filter expressions are explicitly unsupported. Invalid requests return the RFC SCIM error envelope; a PATCH either commits entirely or changes nothing.

New SCIM users receive no instance administrator status, password or team access until a provisioned group's mapping grants it. Existing email addresses require explicit administrator adoption at `POST /api/settings/scim/links`; there is no email-based automatic linking. The administrator may optionally pin provisioning to an existing OIDC provider: **externalId must equal that provider's OIDC subject**, not a guessed email/object ID. The choice applies to newly created/adopted users; each binding remains pinned until explicitly detached. Bound `externalId` changes, self-unlinking that OIDC identity and deleting its provider are refused. Change the SCIM provider setting and detach its accounts before deleting the OIDC provider. Without a pinned OIDC policy, use normal invitations/explicit account linking to establish sign-in separately from provisioning.

Deactivation (`active:false`) disables the account and revokes all browser sessions, workload API tokens and pending security flows. DELETE additionally hides the user from SCIM reads and removes group memberships, retaining the disabled Cove account and its audit history. Recreating the same deleted managed identity can recover the same account ID; a different identity cannot adopt that email. SCIM cannot modify instance administrators. Local manual disablement takes precedence over provisioning reactivation. Group membership refers to SCIM-provisioned User IDs; groups do not map by matching display names, and their `roles` profile attribute never grants Cove privileges. Map their retained IDs through `/api/settings/scim/groups/{id}/mappings`. `/api/settings/scim/links` lists current provisioning ownership for administrator recovery.

The local TLS/PostgreSQL tests replay synthetic identities in documented [Okta](https://developer.okta.com/docs/api/openapi/okta-scim/guides/scim-20/), [Entra ID](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups) and [Authentik](https://docs.goauthentik.io/add-secure-apps/providers/scim/) request shapes. Okta's create-time password placeholder is discarded; legacy Entra string booleans are accepted; Entra membership PATCH and Authentik full replacement/membership PATCH are covered. Fixture files identify their documentation and are not live tenant captures. Deployments still need acceptance with their own IdP mappings and assignment/deprovisioning policies. The implemented protocol follows [RFC 7644](https://www.rfc-editor.org/rfc/rfc7644) and the advertised [RFC 7643](https://www.rfc-editor.org/rfc/rfc7643) schemas within the stated limits.

Instance administrators can read the latest 100 provisioning mutations at `GET /api/settings/scim/activity`, newest first, with time, operation, user/group ID, status and outcome. This uses committed SCIM audit events plus authenticated failed mutation attempts, without recording profile bodies, credentials or raw diagnostics. Empty target IDs represent failed creates before an identity was assigned. Authentication/read failures are separate from provisioning changes.

### LDAP sign-in

Set `COVE_LDAP_ALLOWED_CIDRS` on the panel host to a comma-separated list of the directory servers' narrow address ranges (for example `10.23.40.10/32`); Compose passes this variable from `.env`. An empty or invalid policy refuses directory connections. Resolve and validate **every** address against this operator-controlled list, then dial a pinned address with TLS hostname verification. This deliberately separate network policy allows private LDAP without relaxing HTTP SSRF protection. LDAP connects directly; HTTP proxy settings do not apply. Directory referrals are not followed.

Configure providers at `/api/settings/ldap/providers`: a display name, host/port, `ldaps` or `starttls`, optional PEM CA bundle, service bind DN/password, user/group search bases and filters, `entryUUID` or `objectGUID` as the immutable subject, and email/name attributes. System CAs plus the optional bundle are verified, TLS is at least 1.2, and there is no plaintext/simple-bind or insecure-certificate mode. Omitted/empty bind password on update retains the sealed saved value. User filters must contain `{username}` (for example `(&(objectClass=inetOrgPerson)(uid={username}))`); group filters use `{dn}` and/or `{username}` (for example `(&(objectClass=groupOfNames)(member={dn}))`). Substitutions are LDAP-filter escaped. Exactly one user and a complete, bounded group search are required. Map the returned group DNs to Cove team roles. Test the saved TLS connection/service bind before enabling it for users. A disabled provider can be re-enabled with the host recovery credential; deletion is refused while identities remain linked.

LDAP registration is off unless explicitly enabled per provider, and appears in the security checklist. It never adopts an existing email. Existing users link after signing in locally, supplying directory credentials plus their current password or factor proof; a recent factor-verified session also suffices. The directory email must match the local account when linking. New and existing LDAP sessions use the same second-factor enforcement, login history and account/address lockouts as other sign-in methods. After successful bind and complete searches, only that user's claims for that provider are reconciled. Wrong credentials, TLS/search failures and directory outages cannot remove membership. Group changes affect existing Cove sessions at the user's next successful directory sign-in; LDAP is not a background account-deprovisioning mechanism. Use SCIM for prompt session/token revocation or disable the account locally.

Run `python scripts/test-ldap.py` for a real disposable OpenLDAP/PostgreSQL fixture (loopback-only ports, generated CA/credentials, automatic owned-container cleanup). It checks LDAPS/StartTLS, trust failures, credential/filter boundaries, linking, MFA, lockouts, group changes, outage retention and recovery. `python scripts/test-ldap.py --run 'TestLDAP|TestDirectory|TestGithubTeam|TestSCIM'` also runs the controlled GitHub TLS and SCIM protocol suites. Ordinary `scripts/test.ps1` runs the PostgreSQL suites and skips the explicit native LDAP cases unless the fixture environment is supplied. No external identity provider, SMTP server or collector is deployed or modified by these tests.

`password_login_disabled` controls local Cove passwords, not LDAP directory binds. LDAP remains an external identity provider like OIDC and still requires verified TLS and Cove's second factor. `/auth/sign-in-methods` reports `ldap_enabled` and enabled `ldap_providers` independently of `password_enabled`. Existing administrator password break-glass login remains available. Missing/empty/overlong or malformed LDAP credential fields return a generic 400; well-formed incorrect directory credentials return 401. Neither malformed-input response reveals whether an account exists.

Packaged identity acceptance uses `python scripts/test-browser.py --identity`; UI acceptance uses `python scripts/test-browser.py e2e/directory.spec.ts`. Both hold the shared machine-wide fixture lock, build uniquely tagged panel/worker images and assert this branch's APIs/capabilities. Their disposable OpenLDAP and non-forwarding GitHub CONNECT/TLS provider exercise the production panel binary with fixture-only trust/proxy settings. The browser spec intercepts only GitHub's authorization navigation; the callback still exchanges and reads memberships over actual TLS. Other browser suite invocations skip the directory spec unless its explicit fixture environment is present. No external GitHub/IdP tenant is contacted, and local fixture results do not establish deployed certificate, network or vendor-tenant acceptance.

Fresh installations redirect sign-in to first-user registration. The first successful registration creates the administrator and a secure session without requiring SMTP. Concurrent setup requests are serialized in PostgreSQL; setup closes permanently after the first account. Existing accounts prevent claiming setup. Later accounts require an invitation or explicitly enabled, email-verified registration. SMTP and GitHub settings apply immediately without restarting the panel. Database URL and encryption/API credentials are generated by the installer; they remain private startup configuration because the database and encryption key are needed before saved settings can be read.

Existing installations migrate the administrator, sessions, projects and workloads into a default team. The initial administrator can continue signing in with only the existing password until an email is verified in Account settings. Back up the database and encryption key before upgrading; restore the pre-upgrade database as well as the old binary when reverting this schema migration.

Email/password accounts use verified email addresses, passwords of 16–72 bytes, expiring sessions and one-use password reset links. Configure SMTP host, port, sender and optional authentication in **Settings > Email delivery**, then send a test email. Existing `COVE_SMTP_*` environment settings are imported once on startup. Port 465 uses implicit TLS; other ports require STARTTLS. Certificate verification cannot be disabled. Credentials are encrypted in PostgreSQL using the installation encryption key; saved passwords and client secrets are never returned to the browser. Open registration defaults off and can be enabled in instance settings only when email delivery is configured. Delivery failures are logged without addresses or credentials; monitor these logs and verify delivery before opening registration.

Without SMTP, team administrators can copy seven-day invitation links and instance administrators can generate one-hour password reset links. Share these privately with the intended recipient: possession of an invitation for a new email permits account creation. Existing accounts must sign in as that email before accepting an invitation. Closed registration does not prevent invitations or existing users signing in. A GitHub-only account can set its first password through a verified reset link.

For GitHub sign-in, configure an OAuth App with callback `${COVE_PUBLIC_URL}/auth/github/callback`, then save its client ID and secret in **Settings > GitHub sign-in**. Existing `COVE_GITHUB_CLIENT_ID` and `COVE_GITHUB_CLIENT_SECRET` settings are imported once. GitHub repository access continues to use the App setup in **Integrations**. Cove requests only `read:user user:email`, uses state bound to an HttpOnly browser cookie and PKCE, and does not retain GitHub access tokens. A matching email never automatically links an existing account: sign in with its password and explicitly link GitHub in Account settings. Its email must match a verified GitHub email. Provider credentials and actual SMTP delivery require deployment acceptance; local tests use controlled provider and mail fixtures.

Users may belong to multiple teams. Requests select a team with `X-Cove-Team`; omitting it selects the default team for instance administrators or the first membership for other accounts. Team owners/admins manage membership; only owners can manage other owners. Members receive viewer, operator or editor grants at team, project or environment scope. Viewer permits reads; operator adds deployment, start/stop/restart, rollback, backup and cancellation; editor adds configuration, creation, deletion and restore. Grants combine within the selected team. Legacy API tokens remain workload-scoped; the versioned API also accepts personal/team scoped tokens described below. Both are rechecked against their creator's current account and permissions on every request. Disabling an account or removing its membership removes token access too.

Only instance administrators manage workers, assign workers to teams, manage accounts and change registration. A worker can be assigned to several teams. Assignment controls where new resources may be created; removing an assignment does not stop existing resources or remove their team's access to them.

**Shared workers are not a security boundary against hostile tenants.** Dashboard/API authorization separates team records, secrets, logs and actions, but Compose editors and worker administrators can exercise Docker/host privileges. Use separate workers or VMs for mutually untrusted teams, and do not share the dashboard host with untrusted workloads. Cove does not claim Kubernetes namespace, VM or kernel isolation between teams.

## Workers and deployment

- `POST /api/nodes`: JSON `{"name":"worker-1","address":"worker.example.com","port":22}`. Returns a node ID and a setup command valid for 15 minutes.
- Run the command on the intended worker. Treat it as a credential; do not share it or save it in logs. Registration automatically attempts SSH verification; an unreachable node can be verified again after fixing connectivity.
- `POST /api/nodes/{id}/verify`: verifies pinned SSH identity and probes Docker/Compose. States are `pending`, `enrolled`, `unreachable`, `ssh_verified`, and `ready`.
- `GET /api/nodes`: lists nodes without credentials.
- `GET /healthz`: database readiness.

The installer automatically handles missing prerequisites on Ubuntu/Debian and on RHEL, AlmaLinux, Rocky Linux and CentOS Stream 9 or 10, for amd64 and arm64. Other systemd distributions require preinstalled Docker/Compose, Buildx, OpenSSH, curl, Git and jq. It does not configure firewall rules or VPN connectivity. It refuses to overwrite an unrelated `cove` account or another enrollment. SSH is restricted to structured worker RPC; the systemd worker executes accepted operations independently of SSH sessions. Renewing enrollment preserves the pinned host key.

On Linux, `sh scripts/configure.sh cove.example.com` generates private credentials in `.env`; `docker compose up -d --build` builds the panel, PostgreSQL, and Traefik. For a fresh supported APT or RPM systemd host, `sudo sh scripts/install.sh cove.example.com beta` installs Docker Compose, prerequisites, the packaged dashboard, PostgreSQL, HTTPS ingress and the host update timer. The installer uses the published image version and its matching configuration files, and refuses existing installation directories. This requires DNS and inbound ports 80/443 for certificate issuance. Back up `.env` independently of the database using a separate secure location.

To run workloads on the main node, use `docker compose -f compose.yaml -f compose.local.yaml up -d --build`, then choose **Use main node** in the dashboard. The panel remains non-root and accesses the worker through `/run/cove/worker.sock`. The worker has privileged Docker access and persists state at `/var/lib/cove`; host and container paths must match for workload mounts. Do not run the native systemd worker and the packaged worker against the same state simultaneously. The main worker shares the existing `cove-ingress` proxy with the dashboard. Remote workers create their own owned ingress network, certificate volume and Traefik container. Unrelated resources with these names are rejected. DNS must point each application hostname at its selected worker, with ports 80/443 reachable. Managed routes survive panel outages and worker restarts.

Use `scripts/backup-panel.sh` and `scripts/restore-panel.sh` for panel PostgreSQL backup/recovery; read their arguments and stop the panel before restoring. Preserve the encryption key alongside an independently protected copy of the database backup. A database alone cannot recover encrypted node credentials or workload secrets.

Configure a service's backup policy in its detail page. Local repositories use a dedicated Docker volume. S3 repositories require an existing bucket and use `s3:https://endpoint/bucket/path`, access credentials and an independent encryption password; private CAs can be supplied as PEM without disabling TLS verification. A zero-hour interval means manual backups only. Repository connectivity is checked before stopping containers. Backups then stop the workload to obtain a consistent snapshot of writable persistent mounts and restart it afterward. Storage shared with other running containers is rejected. Retention applies to normal backups; restoration first makes a safety snapshot and does not prune it mid-restore.

Restore verifies repository data, requires the same mount layout, restores files exactly (including removing later files) and restarts only after success. A failed/interrupted restore stays stopped and blocks ordinary start/deploy until a successful restore. Offsite snapshots include `/cove-manifest.json` with configuration and mount metadata. When a restore cannot find local metadata, the worker retrieves and validates it from the encrypted repository using the resource and backup operation IDs. ## Managed proxy listeners

Instance administrators manage node listeners through `GET /api/nodes/{id}/ingress-listeners`, `POST .../initialize`, `POST .../plan` and `PUT /api/nodes/{id}/ingress-listeners`. Workers advertise `ingress_exposures`. Initialization creates a stopped proxy when absent; if a saved managed proxy was removed, it recreates the saved launch, bindings and listener allocation instead of replacing them with defaults. The ordinary route reconciliation path uses the same recovery snapshot.

A plan binds the current proxy identity, launch, running intent, networks, route inventory and proposed settings. Applying requires that exact revision/digest and explicit acceptance that all connections through the node's shared proxy are briefly interrupted. Applications are retained. Public HTTP/HTTPS bindings can be preserved or replaced with explicit IPv4/IPv6 addresses. Private HTTPS and dedicated TCP/UDP listeners receive stable `cove-listener-<id>` entrypoints and internal ports. HTTP/3 adds UDP publication on the HTTPS addresses and requires one advertised host port. Host address availability and external bind races remain subject to Docker; a failed activation restores the retained original. A stopped proxy stays stopped and its publications are tested by an owned inert binding probe before commit. That probe does not reserve host ports while the proxy remains stopped; a later external port claim can still prevent a future start.

Static changes preserve the immutable Traefik image, existing launch/security settings, panel file-copy behavior, persistent ACME accounts/certificates and pinned helper peers. Worker CLI and Cove's three-step Compose static-file launches are supported; unfamiliar scripts, environment-defined entrypoints, external providers, Docker socket mounts, anonymous volumes and unsafe launch shapes are refused before mutation. Compose static replacements use a private file outside the watched dynamic directory. Validation runs a network-isolated Traefik with read-only original mounts, temporary copies of ACME storage and a non-routable dummy authority. Selected stored certificates are checked through verified SNI before stopping and after activation. No proxy receives a Docker socket.

Private worker checkpoints precede mutation. Before durable commit, recovery restores the original container, peer addresses, restart policy and running intent; after commit it finishes deleting the retained original. Recovery runs before initial ingress synchronization, holds conflicting operations and retries while the worker remains available for repairs. Public status/plans contain no environment, private launch configuration or key material. Ordinary dynamic route/file edits retain their existing reload path.

Target-host address/firewall/Tailscale ACLs, external IPv6 and public HTTP/3 acceptance remain separate; a private host binding alone is not a firewall or Tailscale ACL.

Private HTTP routing requires worker route protocol 5 (`submit_routes_v5`). Resource viewers read saved listener metadata through `GET /api/workloads/{id}/route-listeners`; resource editors select `policy.visibility` (`lan` or `tailscale`) and an explicit matching HTTPS `policy.listener`. Select a stored certificate or the proxy default: public ACME is disabled on private routes. All paths and overlapping wildcard/exact hosts use the same visibility/listener. Private routing is separate from the existing resource private-network namespace setting; that isolation mode still disallows proxy routes.

The generated private router uses only its selected listener and a direct-connecting-address allowlist, stacked with route authentication and user allowlists. LAN excludes Tailscale's address ranges. Host-wide public HTTP/HTTPS denial routers prevent unmatched paths falling through to public wildcard or catchall rules; port 80 may redirect before HTTPS denies the request. Custom TCP routers cannot share public HTTP/HTTPS while private hosts exist. Custom HTTP routers must select explicit public entrypoints rather than implicit defaults or managed private listeners, so they cannot bypass the private route's controls. Private listener bindings and reserved priorities are checked before activation and at confirmation. Saved privacy survives omitted-field edits, and durable policies reject older workers instead of silently becoming public. Referenced listeners cannot be removed or reclassified while saved resources or queued operations need them.

Private routes do not create public Cloudflare DNS records. Existing DNS records are not automatically deleted; arrange private DNS and remove public records where needed. All HTTPS listeners on a node share Traefik's single TLS certificate store. A client that guesses an exact private hostname on public HTTPS can obtain that certificate's names, while every HTTP path remains denied; this is an accepted limitation of the current design. For sensitive hostnames, use wildcard or non-identifying certificate names. A private CA avoids public Certificate Transparency logs but does not hide names from guessed SNI; publicly trusted certificates may appear in those logs independently of Cove. ### TCP/UDP workload routes and upstream timeouts

Service routes can also select `protocol: "tcp"` or `"udp"`, an empty `domain`, and an explicit `policy.listener` and `policy.visibility`. Create the matching dedicated TCP/UDP listener on the node Proxy page first; changing published ports uses the reviewed, interrupting proxy replacement. A listener belongs to one raw route across all resources on the node, including queued operations. Raw routes balance the primary service's running containers and up to 15 extra service/port upstreams. TCP passes application bytes and application TLS unchanged; Cove does not terminate raw TLS or issue a certificate for it. HTTP hostnames, paths, auth, headers, redirects, pages, sticky cookies and HTTP timeouts are refused on raw routes. TCP supports direct-source CIDR allowlists and LAN/Tailscale source restrictions. UDP has address binding only: it has no route authentication or source allowlist, and firewall/Tailscale ACL policy remains external.

Raw routes require route protocol 6. Idle sleep cannot observe their activity and refuses them. CPU autoscaling also requires HTTP-only rollout eligibility and refuses raw routes. Parallel replacement strategies fall back to guarded Compose deployment with an explicit reason; promote or abort an existing staged HTTP rollout before adding raw traffic. Stop, Start, Restart and environment pause reconcile raw endpoint addresses without replacing application containers. Paused/stopped routes accept no new forwarding; raw protocols have no HTTP maintenance response. Established TCP connections and UDP sessions can finish until their upstream stops or the session expires. Removing the last UDP route first confirms a transient non-forwarding destination, because the pinned Traefik version otherwise retains the old entrypoint handler after its router disappears. The final configuration contains no retirement router.

HTTP routes can set `policy.timeouts` with `dial_seconds` and `response_header_seconds` (1-600) and `idle_connection_seconds` (1-3600). Omitted/zero fields preserve Traefik's defaults; omit the whole object to leave defaults, or send explicit `null` to clear saved overrides. At least one override is required. Response-header time covers the upstream's initial response, including an upgrade handshake. Idle connection time covers unused pooled HTTP connections, not an upgraded WebSocket's lifetime. WebSocket upgrades work automatically and do not need custom Upgrade headers. `python scripts/test-ingress-listeners.py '^TestIngressExposureTransportRoutesDocker$'` checks actual TCP/UDP balancing, lifecycle refresh, pause/removal, failed-removal rollback, worker recreation, trusted WebSocket upgrades and idle frames, and an enforced HTTP header timeout in an owned isolated Docker daemon. These local tests do not establish target firewall, Tailscale or external port reachability.

Each selected hostname must also be granted to its resource's team in the zone's sharing settings. Reconciliation rechecks the administrator, connection owner, required second factor and team grants. ## Private connections

A private connection gives one source Compose service TCP access to one port of a target service, through a hostname only the source resolves (for example `postgres.internal:5432`). Connections are directional: replies use the same TCP connection, but the target cannot open connections to the source unless a separate connection exists in that direction. Grants are never transitive. Public domains, published ports, shared networks and Tailscale access are unchanged. UDP is not forwarded.

Create, edit and remove connections from an environment's or project's resource graph (or list), or with `POST /api/private-connections`, `PUT|DELETE /api/private-connections/{id}` and `POST /api/private-connections/{id}/retry`. `GET /api/projects/{id}/connections[?environment=ID]` returns the graph. Creating or editing needs editor access to both resources; either side's editors can remove a connection, and operators of either side can retry. Endpoints the caller cannot view are returned without names, services, hostnames or worker details. Both resources must be in the same team; they may be in different projects and environments. Targets must be services; previews and services using Tailscale access cannot be endpoints.

Each worker runs one `cove-link` gateway container built locally from the worker binary (no image is pulled). For every (source service, hostname) the worker creates an internal network containing only that service and the gateway, and for every target service an internal network containing only that service and the gateway. The gateway listens only for the ports granted on each source network, checks that callers come from that network, and forwards only to addresses on the target's network. Containers are attached with `docker network connect` and on the next deploy through Compose; nothing is started, stopped or restarted, so manual stops are kept. Link networks use /27 subnets from `10.250.0.0/16`; set `COVE_LINK_POOL` in the worker environment to another unused IPv4 range if that one overlaps a host or VPN route.

Between workers, gateways use TLS 1.3 with mutual authentication. Each worker generates its own key under `/var/lib/cove/links/identity` (it never leaves the node) and the control plane pins each peer's key fingerprint per connection. The target's gateway accepts a connection only from the pinned source worker and only for that connection's port. Cross-worker connections need the target worker's link port (TCP 47800 by default) reachable from the source worker; Docker publishes it on all host addresses, and connections to it have their own limit so they cannot exhaust local link capacity. No VPN account or token is needed. The peer address defaults to the node's SSH address; instance administrators can set a different address and port with `PUT /api/nodes/{id}/private-links` (required for the main node's local worker). Changing the port recreates that worker's gateway, briefly dropping its open link connections.

The control plane sends each worker its complete link configuration and shows a connection as Active only after both workers confirmed its current version. Unreachable workers are retried with backoff, ambiguous replies are resent safely, and workers reapply their saved configuration every 30 seconds, after each operation and after restarts, without the control plane. Revocation removes listeners and closes open connections before other changes; a gateway that cannot confirm a revocation is stopped. Removing a connection takes effect as soon as either worker applies it, and the connection stays listed as Revoking until both have. Link networks are kept for rollback and removed with their workload. Workers report `private_links` after upgrade and verification; upgrade every worker that hosts an endpoint before connecting it.

Containers in one resource still share its Compose network, and resources on a shared network reach each other on every port. The graph shows shared networks as dashed lines and warns where they give broader access than a connection. Shared workers are still not a boundary against hostile tenants: Docker access on a node can bypass link networks. `python scripts/test-private-links.py` runs the cross-worker acceptance on two disposable Docker-in-Docker nodes.

## Environment previews

A project's preview recipe (**Project → Previews**, `GET|PUT /api/projects/{id}/preview-recipe`) copies one production environment for each branch name that matches a prefix pattern (default `staging/*`) in the selected GitHub App repositories. The part after the prefix names the preview, so `staging/checkout` in the web and api repositories is one preview. Only project editors who can edit the production environment save recipes; saved changes apply to previews created afterwards. Turning a recipe off stops new previews and branch updates; existing previews keep running until they are removed. Previews are listed with `GET /api/projects/{id}/environment-previews` and managed with `/api/environment-previews/{id}` (`approve`, `retry`, `redeploy`, `refresh`, `credentials`, `PUT {pinned}`, `DELETE`). A preview environment grants exactly the access of its production environment, including environment-scoped grants; viewers can read it, operators retry and redeploy, editors approve, refresh, pin, delete and read credentials.

**What runs.** When a preview is created, Cove pins every included resource's production state: the commit of its latest successful deployment (rollbacks resolve to the release they restored), its Compose, and the exact image IDs of that release, which the preview tags so they survive production release pruning. Resources from a selected repository with a matching branch build that branch's head; everything else runs the pinned production state with the pinned images. A push redeploys only that repository's resources. A branch created later in another selected repository joins the preview and moves only its resources. Deleting a branch returns its resources to the pinned production state; the preview is removed only when every participating branch is gone, after the inactivity period (pushes and preview actions count as activity; traffic does not), or when deleted. A removed preview stays removed: the periodic scan does not re-create it from the same branch heads, but a new push to a matching branch or **New preview** starts a new one. Pinned previews are kept. Production deployments never advance a preview's pinned state. Jobs never run unless the recipe enables their schedule. Services that serve no domain, receive no preview connection and nothing in their resource depends on are treated as background services and start disabled; each can be switched on.

**Data.** Each preview copies its data once, when it is created, from read-only sources. PostgreSQL and MariaDB resources with a logical backup policy are copied from a fresh `pg_dump`/`mariadb-dump --single-transaction` snapshot streamed out of the running production container, then restored into the preview's own database before any preview service starts. The restore is verified table by table against the snapshot's row counts, and the snapshot time is shown per resource. Each database is consistent in itself; several databases are not snapshotted at the same instant. Other volumes and host directories are copied file by file from a read-only mount into preview-owned volumes and verified by a content digest; a source that keeps changing during three attempts fails the copy. Volumes of recognised database images without a logical backup policy cannot be copied this way and must start empty; cache images default to empty. TimescaleDB, non-InnoDB MariaDB tables, single host files, devices, privileged or host-namespace services and unpinned job images are explicit blockers. A free-space check runs before copying. Pushes and redeploys never repeat a copy or reset data. **Refresh data from production**, confirmed by typing the preview's name, stops the preview's containers, replaces its databases and copied volumes with a new snapshot and redeploys. Schema migrations that run in a preview change only the preview's database; nothing is rolled back in production because nothing is written there.

**Isolation.** Every storage mount of a preview resource, including volumes a branch adds, is rewritten to a volume the preview owns; host ports, fixed container names, external networks and pinned subnets are dropped, and privileged options, host namespaces and unplanned host mounts are refused at deploy time. Private connections, shared networks and resource variable bindings between resources of the production environment are recreated between the preview's copies with the same hostnames, so connection strings that name them reach the copies. Dependencies on resources outside the environment, external networks and Tailscale access must be omitted explicitly; previews never join production networks. Manual private connections, variable bindings, configuration changes and new resources in preview environments are refused; stop, start, restart and temporary database access remain available.

**Variables and external effects.** Variables whose names look like credentials or endpoints (secrets, tokens, passwords, URLs, hosts, mail, payment and storage keys) need an explicit decision: copy the production value, use a preview value or remove it. Values that only name services inside the preview are copied, and so are plain settings. Override values are sealed and never returned by the API. Cove cannot stop application code from contacting external services with credentials the recipe copies: use sandbox credentials or remove them.

**Routes and access.** With a domain template such as `{resource}-{preview}.preview.example.com`, each routed production resource gets a preview hostname. Branch suffixes are reduced to DNS-safe names; long or colliding names get a short hash. Hostnames inside a Cloudflare zone registered in Cove must be shared with the team; with DNS automation enabled for the zone and node, Cove creates the address records and removes them with the preview, otherwise point the names (for example a wildcard) at the node. Routes are published only after every resource deployed successfully. Private previews (the default) require a per-preview username and password through the proxy; editors read them in the preview page, and each reading is audited.

**Workflow and safety.** Creation advances through recorded stages (approval, plan, data, connect, deploy, publish) in the dispatcher; each stage re-reads its state, so retries, control-plane restarts and repeated webhooks resume rather than repeat, and the plan stage creates the environment and its resources in one transaction. New previews wait for an editor's approval by default, because anyone who can push a matching branch could otherwise obtain a copy of production data; creating a preview from the Previews page counts as approval. Webhook deliveries are verified with the GitHub App secret, deduplicated, and treated as hints: the branch head is read from GitHub before anything changes, so replayed, stale or out-of-order deliveries cannot move a preview backwards, and a periodic scan catches missed deliveries. Only repositories connected to the production environment through an installation shared with the team are considered; forks have their own repository IDs and are never matched. The recipe limits concurrent previews, and further branches wait with the reason shown. A failed preview keeps its data; a new push after a failed deployment retries it, and Retry repeats only failed steps. Removal runs one resource at a time through the worker, which refuses anything without the preview ownership marker.

**Limits.** Previews run on the same nodes as their production resources and count against team quotas with the production resource limits. Workers report `environment_previews` after upgrade and verification. Copies and restores of large data take time and disk on those nodes. Every preview resource adds a Compose network on its node; with Docker's default address pools a node holds only about 30 networks, so set `default-address-pools` with smaller subnets (for example /24) in the Docker daemon configuration of nodes that host previews. Logical snapshots read production databases while they serve traffic. Preview data that the application writes outside Cove-managed storage is not tracked. GitHub must deliver `push` events to the App; branch access uses the installation's contents read permission.

Control-plane workflow tests run with `COVE_TEST_DATABASE_URL` (`go test ./internal/control -run EnvironmentPreview`). `COVE_E2E=1 go test ./internal/control -run TestEnvironmentPreviewDockerAcceptance` runs the Docker acceptance against a real worker in a privileged Docker-in-Docker fixture over SSH, an HTTPS Git server with real branches, PostgreSQL, MariaDB, Redis and application containers; GitHub's API and webhook deliveries are simulated in process from the real repositories.

Job schedules expose `overlap_policy` (`skip`, `queue_one`, `replace`), `timeout_seconds` (5–86400; default 1800) and read-only `pending_since` on the existing schedule API. Omitted fields preserve settings; saving a schedule clears its pending tick. `queue_one` retains one coalesced run, while `replace` cancels only an executing job and waits for its terminal cleanup before queuing another. Queued approvals, builds and other operations are never preempted. Missed calendar ticks do not replay in a burst. Manually stopped jobs suppress schedules and discard pending runs. Explicit `POST /api/workloads/{id}/operations` with `action: deploy` runs now and resumes scheduling; existing approval, freeze and window rules still apply. Disabling cron preserves execution settings.

Upgraded workers advertise `job_runs`. Their job timeout starts after source/build preparation (which retains its separate 30-minute bound), and includes Compose startup, dependency initialization, missing-image pulls and the designated service's execution. Every run-owned service has restart policies disabled, including dependencies. A successful init container does not terminate the main job. On completion, timeout or cancellation, all run containers are stopped before the operation becomes terminal. The bounded redacted operation log includes stdout and stderr. `result.job` reports optional exit code, timeout, confirmed cleanup and any unavailable container logs. Worker restart observes the original containers and deadline without rerunning them; Docker unavailability retains the workload lock. Legacy interrupted jobs have an unknown outcome and are stopped before unlock. This cannot undo job writes or guarantee an application-level transaction. Existing notification integrations receive job failure events. Old workers retain their default execution behavior and cannot use advanced settings.

`COVE_TEST_JOB_DOCKER=1 go test -v ./internal/worker -run '^TestJobDocker$' -count=1 -timeout 4m` requires a disposable Linux Docker daemon with Compose and cached BusyBox 1.37. It checks init completion, stderr and secret redaction, nonzero exits, timeout, cancellation, stopping dependencies and continuation in the same container across a worker kill/restart. Never run this fixture on a daemon with real workloads. `scripts/test.ps1` covers the PostgreSQL overlap and pending-run policies.

`GET/PUT /api/workloads/{id}/restart-policy` reads or configures `{enabled: boolean}` for automatic Docker-health restarts (read/edit permission). Responses include the last queued attempt, operation ID, attempts in the last hour, oldest attempt still in that window, and any unavailable-health message. It defaults off, requires worker capability `unhealthy_restart` to enable, and excludes jobs and managed previews. Disabling cancels queued automatic attempts; an attempt already executing may finish. Monitoring runs about once a minute while the panel is online, with a five-minute resource cooldown and at most three queued attempts per rolling hour. It waits for other operations and staged rollouts. Healthy, starting, stopped and containers without a Docker healthcheck are never restarted by this policy. A restart can interrupt traffic and cannot repair a failing application; use healthchecks suitable for restart decisions. At most 64 unhealthy containers are handled by one attempt. Each `restart_unhealthy` operation uses normal audit, locking, cancellation, interruption and notification behavior; interrupted restarts must be inspected rather than assumed rolled back. No image is pulled or rebuilt. `COVE_TEST_UNHEALTHY_DOCKER=1 go test ./internal/worker -run '^TestUnhealthyRestartDocker$' -count=1` requires an isolated Linux Docker daemon and cached BusyBox 1.37; it proves recovery of an unhealthy container while preserving healthy and stopped containers.

## Environment suspension

`GET/PUT /api/environments/{id}/suspension` reads or requests `{paused: boolean}` (environment read/operate permission). Repeating a request retries failed resources. Workers must advertise `suspensions`; managed preview environments retain their preview lifecycle. The response separates desired `paused` from confirmed `phase` and lists each resource's operation, resume intent and error. An unreachable worker remains pending. Pause cancels active work and waits for terminal cleanup before queuing durable worker suspensions. New resources in a paused environment remain stopped. Deployment/start/restart/promotion/restore/drill admissions are blocked; automation drops paused pushes and job ticks. Configuration, route edits, builds, metadata reads, backups, Stop and Abort remain available subject to normal workload locks. Placement changes require the environment to finish resuming.

The worker captures owned container IDs, completion state and original Docker restart policies before disabling restart and stopping them. It retains authenticated HTTP routers with empty upstreams returning 503; it does not remove host claims or weaken route protection. Pause intent survives worker restarts, including interrupted cleanup. Resume starts the same previously running service containers, waits for available Docker health checks within a persisted two-minute deadline, restores restart policies and then exposes traffic. It preserves manual stops, completed init containers and staged rollout weights; jobs wait for their next future scheduled tick rather than running during resume. Abort can remove a paused candidate without starting the old generation. A missing container or failed readiness keeps the captured workload stopped and reports an error. Set desired pause off and retry the environment action, or explicitly deploy/start/restart the failed resource to repair it. A restore can repair storage while retaining the pause marker; retry resume afterwards. Pause is disruptive and does not reverse application writes or replace a backup. Disconnected workers cannot stop until communication is restored.

`COVE_TEST_SUSPENSION_DOCKER=1 go test -v ./internal/worker -run '^TestSuspensionDocker$' -count=1 -timeout 12m` uses an isolated Linux Docker daemon with Compose and cached BusyBox 1.37 / Traefik. PostgreSQL tests use `COVE_TEST_DATABASE_URL` with `go test ./internal/control -run '^TestEnvironmentSuspensionIntentAndRecovery$' -count=1`. These commands must not target a daemon hosting real workloads.

## Idle sleep and local wake

`GET/PUT /api/workloads/{id}/idle-policy` requires workload read/edit access. PUT accepts `{enabled, after_seconds, request_driven}` and queues an `idle_policy` operation; settings are saved only after it succeeds. The interval defaults to 300 seconds and accepts 60 through 86,400. Enabling requires the explicit assertion that the whole app is request-driven. The worker must advertise `idle_sleep`. Jobs and managed previews are excluded. Every running service needs a passing Docker healthcheck and managed HTTP route; completed init services stay completed. Published host ports, private connections, shared/external networks and staged rollouts prevent sleep. New deployments and route edits preserve these restrictions; private connections cannot be added until sleep is disabled.

The worker checks about every 15 seconds. Active requests, including full SSE/WebSocket lifetimes, prevent quiescing. Sleep stops captured containers and temporarily disables their restart policies. An authorized request waits for the same containers to resume, pass a fixed two-minute health deadline, and regain current upstream addresses; the gateway bounds waiting to three minutes. A failed episode returns 503 and cannot repeatedly restart the app. Repair it and use Start to retry explicitly. Deploy/rollback must wait until a sleeping resource is started; Stop and environment pause prevent request-triggered wake. Disabling sleep wakes an idle resource and restores direct ingress before removing the helper; disabling in a paused environment leaves it stopped.

Runtime reads add authoritative `idle` status, active request count, idle timer reset time and last sleep/wake timestamps. The timer can reset on activation or helper restart, so it is not a last-request timestamp. Worker-local sleep/wake operations have no control-plane operation IDs; only policy changes appear in normal operation history. The helper runs read-only without capabilities or Docker access, with a 128 MiB memory cap, bounded logs and scoped Unix sockets. Its internal front /29 and backend /24 networks use `COVE_LINK_POOL` (default `10.250.0.0/16`) without overlapping private-link networks; an operator-supplied pool must accommodate /24 networks for this feature.

Use `go test ./internal/worker -run Idle` for policy/traffic/security/journal tests. Real acceptance requires a disposable Linux Docker daemon with Compose, cached BusyBox and Traefik: `COVE_TEST_IDLE_DOCKER=1 go test -v ./internal/worker -run '^TestIdleDocker$' -count=1 -timeout 12m`. It owns the managed ingress name and ports inside that isolated daemon. PostgreSQL tests use `COVE_TEST_DATABASE_URL` and `go test ./internal/control -run IdlePolicy`. Acceptance on target Docker hosts still needs the application's cold-start/health behavior, long-lived traffic, host restart and network-pool suitability checked; local fixtures do not establish production suitability.


## Deployment verification

Environment preview routes retain their source route policies and use the preview's hostname/basic authentication; additional routed upstream services are included in the preview plan. Publishing a preview of a resource with a fixed hostname redirect is blocked because that redirect could send preview users to production. Remove the redirect or exclude the resource first.

Managed route JSON accepts an optional `policy` with `path_prefix`, `request_headers`, `response_headers`, `security_headers`, `ip_allow_list`, `redirect_host`, `redirect_permanent`, `certificate_source`, `upstreams` and `sticky`. Omitted policy keeps existing host/basic-auth behavior. Prefixes are literal `PathPrefix` matches and are not stripped; a resource may have multiple prefixes on one hostname, while hostname ownership remains exclusive across resources. Upstreams are additional `{service,port}` Compose services from that resource (up to 15), balanced equally with the primary service; they do not create replicas. Sticky sessions use a secure HttpOnly SameSite=Lax cookie. HTTP continues redirecting to HTTPS globally. A redirect preserves path/query and uses 302 by default or 301 when permanent.

Service configuration optionally accepts `rollout`: `strategy` (`disabled`, `rolling`, `blue_green`, `canary`), per-service `replicas` (1?16, 64 total including defaults), `http_checks` (`{port,path}` on container loopback), `parallel_volumes`, `drain_seconds` (0?120), `timeout_seconds` (5?600, default 120), and `canary_percent` (1?99, default 10). Missing replica settings mean one container per service. A PUT omitting rollout preserves the saved settings; use `strategy: disabled` to opt out. Legacy resources retain their previous deployment behavior. Workers must advertise `rollouts`; upgrade and verify before using the controls. Configuration changes apply on the next deployment.

Parallel replacement requires a managed HTTP route and health checks for all services (Docker checks from Compose or the image, otherwise an explicit HTTP check). It rejects fixed/public host ports, fixed container names or addresses, host namespace sharing, privileged/device/capability settings, links/profiles, external or explicit-IPAM networks, shared/private connections and deployment hooks. Writable mounts and image-declared volumes require an explicit assertion that concurrent writers are safe; do not assert this for a single-writer database. Compose must fit the 32-service/64-container bounds. Ineligible configurations use guarded replacement, report the reason in logs and `result.rollout.reason`, and may interrupt traffic. Guarded mode uses Compose scaling rather than rollout replica overrides.

Eligible rolling deployments start isolated service/network generations, wait for all replicas to be healthy, atomically switch the file-provider traffic configuration, wait the drain interval and stop/remove only the owned old container IDs. HTTP checks permit only loopback HTTP, reject redirects and require 2xx; they cannot fetch remote metadata. An unsuccessful health gate or cancellation before the persisted traffic decision restores the previous traffic and release. Recovery keeps the workload locked until Docker and Traefik confirm the outcome; a decision already committed finishes cleanup after a worker restart. Applications must still tolerate concurrent startup and traffic; Cove does not roll back application writes.

On an existing release, blue/green holds a healthy candidate at 0% and canary sends the configured percentage to it. `GET /api/workloads/{id}/runtime` returns authoritative `rollout` state with operation/release IDs, strategy, phase, candidate percentage and replica overrides. Operators use `POST /api/workloads/{id}/operations` with `action: rollout_promote` or `rollout_abort`. Promote rechecks health, switches to 100% and drains; abort restores the old release and removes the candidate. Promotion respects deployment approval, window, freeze and quota; abort remains available for recovery. Another deployment, rollback or backup must wait for resolution. Stop first aborts a pending candidate. Route edits remain durable and are retained on promote/abort. The first deployment has no old release and commits immediately for all strategies. Staged candidates are not retained rollback releases until promotion.

Local rollout acceptance uses `COVE_TEST_ROLLOUT_DOCKER=1 go test -v ./internal/worker -run '^TestRolloutDocker$' -count=1 -timeout 12m` inside a disposable Linux Docker daemon with Compose, cached BusyBox and Traefik. It continuously sends HTTPS traffic through real Traefik while replacing replicas, failing health gates, shifting/aborting/promoting weighted generations, restoring immutable releases, cancelling and killing/restarting the worker. Do not run it against a daemon hosting real workloads: its fixture owns the managed proxy name and ports inside the disposable daemon. External public TLS and target-node behavior still require staging acceptance.


Resource reads omit basic-auth hashes. Route and resource updates preserve an omitted `auth` for the same hostname/path; changing the prefix also preserves it when that hostname's existing credentials agree. An ambiguous prefix change is refused until authentication is supplied explicitly through the API. Explicit `auth: ""` removes authentication, while an explicit bcrypt entry replaces it. A new hostname needs its own authentication setting. Saving advanced policies cannot silently remove the existing route's protection.

The security preset applies one-year HSTS without subdomains/preload, nosniff, frame denial and strict-origin-when-cross-origin referrer policy. Custom headers reject case-insensitive duplicates, control characters, proxy identity/connection headers and preset conflicts. Source allowlists accept up to 64 IPv4/IPv6 CIDRs and use the direct connection peer, not caller-supplied forwarded headers; behind a CDN this is the CDN address. These restrictions do not create private address bindings. Certificate source `acme` (the default) uses the existing resolver; `default` disables ACME for that route and uses the proxy default certificate, which may be self-signed unless explicitly provisioned through proxy configuration. This is not certificate upload or Origin CA provisioning. Upgrade and verify the worker before using policies. Route changes retain existing journal, cancellation and rollback semantics. `go test ./internal/worker -run RoutePolic` tests validation/generation and `COVE_TEST_DATABASE_URL` enables `go test ./internal/control -run RoutePolicy`; the existing custom-ingress Docker test also validates the generated policy configuration against real Traefik.

Routes on workers reporting `route_protocol: 2` also support `policy.maintenance` (`enabled`, optional `html`), `policy.error_pages` (exact HTTP status to HTML) and `policy.forward_auth`. Maintenance returns 503 with Retry-After and retains basic auth, source restrictions and forward-auth. Error pages preserve the application status and do not replace authentication failures. HTML is limited to 16 KiB per page, eight error statuses from 400 to 599 and 64 KiB combined error HTML per route. Pages have no-store caching and a restrictive CSP: scripts and external assets are disabled; inline CSS and data images are permitted. Do not include secrets in page HTML.

Forward-auth accepts either a public, verified HTTPS `url` or an owned Compose `service`, `port` and optional `path`; private network URLs outside the workload are rejected. Public DNS answers are checked together and connections pin a validated public address, without redirect following or environment proxies. The provider receives a GET with original request metadata, cookies and authorization, with a 15-second timeout and 32 KiB response limit. Select the provider's verification endpoint (for example Authelia, Authentik or oauth2-proxy), not its login page. Configured `response_headers` replace client identity headers, and `response_cookies` names select refreshed cookies. Forward-auth cannot depend on another protected forward-auth endpoint. An idle-sleep resource needs an independent public HTTPS provider; it cannot sleep its own authentication service.

Route updates preserve omitted maintenance, error-pages and forward-auth fields for the same hostname/path. Send explicit `null` for each setting being removed; an ambiguous path change with different existing protection is rejected. Workers use a versioned submit method and protect route-bearing journals, ingress inventory, releases and backup manifests so an older binary rejects the saved certificate source instead of ignoring a new auth gate. This guard is internal to worker files and is absent from API responses. Older workers must be upgraded and verified before these settings can be deployed.

Page serving and auth checks use a bounded, read-only worker helper with no Docker socket or management credentials. Its immutable configuration, trusted proxy peer and owned auth replicas are compiled from the current route inventory. Proxy confirmation includes the helper revision; failed changes restore the previous route through the existing durable journal. Helpers restart independently of the panel and worker. Retired helpers are removed only after active proxy confirmation and a graceful drain. Linux acceptance: `COVE_TEST_ROUTE_AUX_DOCKER=1 go test -v ./internal/worker -run '^TestRouteAuxiliaryDocker$' -count=1 -timeout 12m` in a disposable Docker daemon with cached BusyBox and Traefik. Never use a daemon hosting real workloads for this fixture.

Keep deployment-specific hostnames, IP addresses, credentials, operation IDs, backup locations and acceptance logs in a private operational record outside the source repository. Example hostnames in this documentation are illustrative. Back up the encryption key independently of the database, and verify recovery on the target infrastructure.

Traefik handles dashboard and worker ingress through a watched file provider without a Docker socket mount. Its management API binds only to the proxy container's loopback interface; only ports 80 and 443 are published. The dashboard route is maintained separately from worker routes. Updates are atomic, and workers confirm active routers before accepting a deployment. Route changes on a deployed service run as a `routes` operation that updates only the proxy and attaches route services to `cove-ingress`; containers are not restarted or started, and the saved routes change only after the worker confirms them. The worker journals the previous routes before touching the proxy and commits only after the proxy and its release state hold the new ones; failure, cancellation or a restart before the commit restores the previous routes, and the operation stays running, keeping its hostnames claimed, until that restore is confirmed. Services with no deploy attempt store routes for their first deploy. Certificates persist in `/data/traefik-acme.json` with mode 0600. Custom ACME testing uses a trusted CA certificate rather than disabling verification.

Instance administrators can manage custom Traefik dynamic configuration (HTTP, TCP, UDP and TLS) per node under **Nodes → node → Proxy configuration**. Files live in the proxy volume's `/data/dynamic` beside the generated `routes.yaml` and `panel.yaml`, which stay read-only, as do `cove-` names. Existing files such as migrated certificate or legacy route files are listed as not imported; importing adopts them byte for byte without touching the proxy, reporting existing conflicts as warnings. Every save names the revision it edits, rejects new conflicts (reserved or duplicate object names, hostnames Cove routes, catch-all TCP routers on shared entry points, unknown entry points or resolvers, certificate paths outside `/data/` or inside Cove's dynamic, history, ACME and credential files), then loads the full directory with the candidate in a network-isolated Traefik of the same image with the proxy volumes mounted read-only. Only errors the live proxy does not already report block a change. The worker journals the previous file in `/data/cove-custom-history/<file>/` before an atomic rename, confirms the live proxy loaded the new objects without restarting it, and otherwise restores the previous file; a restore that cannot be confirmed blocks further changes and retries until it settles, including after a worker restart. Removed files are moved to that history directory, which keeps the ten most recent versions per file. Changes are refused while the worker drains, during a staged same-host migration, or when the proxy is stopped; Cove never starts, restarts or recreates the proxy for them. Entry points, published ports and certificate resolvers are static settings shown read-only: adding a TCP/UDP port needs a separately planned proxy recreation. TLS sections and servers transports are not reported by Traefik's API, so their activation is confirmed by file revision after validation. Resource routes cannot claim a hostname a managed custom file routes. `COVE_TEST_INGRESS_DOCKER=1 go test ./internal/worker -run TestCustomIngressDocker` exercises this against a real Traefik on a Docker daemon without an existing `cove-ingress`.

Workers refuse to overwrite an existing proxy using a different image family. Older installations require an explicit proxy migration with protected recovery copies of the deployment configuration, worker binary and certificate state. Preserve the previous certificate data separately from Traefik's ACME state until the migration is verified.

Traefik acceptance passed real Pebble challenge validation, trusted issuance, renewal, restart persistence and CA outage; systemd installation and failed-upgrade recovery; and shared dashboard/local-worker routing, last-route removal/restoration without proxy restart, and control-plane outage. The expanded route test caught and fixed Traefik rejecting empty nested configuration maps. Both packaged browser workflows, Go tests/vet/race checks, frontend lint, 26 frontend tests and the production build passed for that revision. Live checks additionally covered public HTTPS, redirects, worker/proxy restarts, remote deployment, last-route removal/restoration, matching worker binary hashes and management API isolation from the application network. These results do not replace acceptance on a new deployment.

Project deployment sequences can be saved and reused. GitHub-triggered sequences require all steps to have automatic deployment enabled for the same repository and branch; each uses the pushed commit. A stopped or unmatched step suppresses the entire sequence. Failed or cancelled prerequisites cancel later operations; migration effects are not automatically reversed.

Same-host Coolify migration uses explicit staged ingress, cold storage copies, per-domain bridges and a recoverable proxy handover. See the operator's internal migration runbook for prerequisites, commands and the rollback boundary. The operator tools never start legacy application containers or overwrite their source storage.


### Operational safety checks

Resource editors can browse files in their own running workload containers and attached Cove-owned named volumes through `/api/workloads/{id}/files` and its `targets`, `content`, `metadata`, `limits`, `upload` and `download` endpoints. Every endpoint requires Edit configuration and Read secrets, including reads; these catalogue permissions are checked independently. Every read/list/download and mutation is audited by resource/action without file contents, and responses are not cacheable. Contents travel over the restricted transport; uploads use process stdin rather than command-line arguments. Hosts, external volumes and arbitrary Docker objects are not independent file targets. Container views include that container's filesystem and mounts; shared Docker hosts are not hostile-tenant isolation.
To build without deploying, connect a resource to a team registry and queue `POST /api/workloads/{id}/operations` with `{"action":"build","build":{"repository":"team/app","no_cache":false}}`. The repository is a lowercase path within the selected registry, without a tag or hostname (maximum 128 characters). Workers must advertise `build_publish`; Compose must support named Buildx builders and Docker push must support platform selection. Builds include all Compose services with a build definition (one to 64), publish only the locally built platform and return `result.build.images` entries containing `service`, `image_id` and an immutable `reference`. Use those references in Compose for a later deploy; publication does not deploy automatically. Jobs can build without running; managed previews cannot queue builds. Deployment approvals/freezes apply to the later deploy, and a build preserves the resource's stopped intent.

Build output streams through the existing bounded/redacted operation log. Builds reuse the worker-owned persistent BuildKit builder, with per-build cache bypass and automatic bypass for secret mounts. Existing cleanup runs every six hours, pruning cache older than seven days toward a 2 GB retention target; this is not a hard disk quota. File secrets selected for build services use BuildKit secret mounts, not build arguments. Dockerfiles must consume the mount without copying it into their output; redaction cannot prevent application build code from embedding secrets. Registry authentication files are outside the workload build context. Temporary build tags, generated inputs, checkouts and file secrets are removed after completion/cancellation and retried during interrupted-build recovery. A failed cleanup fails the operation and retains the marker for the next build. A partially successful push may leave artifacts in the registry; no remote deletion is attempted. Interrupted builds are not replayed automatically.

`COVE_TEST_BUILD_DOCKER=1 go test ./internal/worker -run TestBuildPublishDocker -count=1` runs on an isolated Linux daemon with cached `busybox:1.37`, `registry:2.8.3` and `moby/buildkit:buildx-stable-1`. It builds with a real secret mount, publishes to a disposable loopback registry, verifies the pulled immutable image, secret absence and log redaction, and checks that an existing container and release are unchanged. Native Windows workers skip this acceptance because their loopback differs from Docker Desktop's daemon. Dedicated build nodes, buildpack detection, static-site mode and a new CI-image preview pipeline are not implemented.

`POST /api/workloads/{id}/operations` accepts `action: "image_check"` for services on workers advertising `image_lifecycle` (Docker Buildx must be available). The operation checks up to 64 deployed containers without pulling or replacing them and saves per-image results; `GET /api/workloads/{id}/images` returns the latest successful check with a timestamp and `stale` flag after a newer deploy/rollback. Results distinguish current, update available, pinned, unpublished and unknown; registry failures are sanitized and do not imply the image is current. Local images without matching registry digests cannot be checked. Multi-platform checks compare the matching platform's configuration digest, avoiding false updates caused only by another architecture. Release links are derived from deployed OCI GitHub source/version labels and are not verified changelogs.

Background image checks run hourly for ready, deployed, non-stopped resources outside previews. Jobs additionally require worker capability `job_image_lifecycle`; checks inspect the containers retained by a successful or failed run and never execute the job, pull images or start containers. The selected job service must still be retained, so dependency-only leftovers cannot appear as complete coverage. Never-run jobs return a clear failure in the operation log. A newer job run attempt makes the cached result stale even when that run failed. If an image check occupies the job's operation slot when a cron tick arrives, one pending execution is retained even under Skip, without cancelling the metadata check. It is queued after the check finishes. Ordinary overlap handling for actual job runs is unchanged.

Image checks reuse durable operations and workload locks, cap concurrent background checks at four, and do not generate generic deployment notifications. Digest checks alone never redeploy. ### Environment files, built-ins and external secrets

Resource **Variables** supports saved `.env` import/export alongside per-key edits. Import accepts at most 1 MiB and 256 names (64 KiB per value), merges supplied keys, supports comments, `export`, quoted/multiline values and last-assignment-wins semantics, and rejects reserved process/Compose names. Dollar expressions remain literal. Import saves configuration without deploying. Export requires the same editor permission as other variable edits/secret reads, records a disclosure audit before sending values, and exports raw saved references rather than contacting external providers. Downloads can contain credentials; handle them as secrets.

`GET /api/workloads/{id}/variables/builtins` lists canonical definitions and worker availability. On upgraded, verified workers, each deployment automatically receives `COVE_FQDN`/`COVE_URL` from its first public route, its actual Git `COVE_COMMIT_SHA` and selected `COVE_BRANCH`, environment/project names, and `COVE_RELEASE` (operation ID). Inapplicable fields are empty. Defaults are usable in Compose `${COVE_PROJECT}` interpolation, container environments and Dockerfile `ARG` declarations. Explicit saved variables and explicit Compose service environment/build-argument entries take precedence. Existing workers must be upgraded and verified before automatic defaults are available.

Manage team-scoped external connections in **Integrations > Secret providers**. Creating a connection saves credentials without claiming to authenticate successfully. Names and configuration metadata are readable; credentials remain sealed and cannot be read back. Only name/token can be changed in place (a blank token preserves the saved credential); create a new connection for different endpoints or scopes. Removing a connection causes unresolved references to fail future deployments. Already-prepared operations retain their sealed snapshot.

Set a variable to `{{secret.CONNECTION_ID:REFERENCE}}`, using the actual saved connection ID. These references also work through existing shared/resource variables. Each deployment resolves references after the shared/resource bindings, caches each reference only within that operation, then seals the resolved snapshot for immutable retries. Provider values are not recursively interpreted. Rotation is picked up by the next new deployment. Failures identify the variable without exposing credentials, provider error bodies or returned values. Environment preview recipes require explicit copy/override/remove decisions for external and shared references.

### Versioned public API, CLI and MCP

`GET /api/v1/openapi.json` serves OpenAPI 3.1 from the same route catalogue that registers the real handlers (`public_api.go`). The authenticated **API reference** page bundles Swagger UI locally and uses the existing session cookie and selected team for Try it out; it does not store bearer credentials or contact a CDN. The API exposes project/environment CRUD, saved resource configuration, routes, operations/runtime/logs, saved variable import/export, per-variable existence/revision and bounded exec/tunnel leases. Configuration saves are separate from asynchronous deployment. Error responses are plain text; successful responses are JSON. Existing `/api` browser/workload-token routes continue to work.

Create personal/team credentials in **API keys**. Permissions are explicit scopes listed by `/api/access-tokens/scopes`; the catalogue and its current numeric grant mapping live in `access_tokens.go` so the parallel custom-role/auth track can reconcile them in one place. Personal tokens follow the creator's current grants in the team selected by `X-Cove-Team`; team tokens are fixed to their team and require a team administrator to create. Both expire in 1–365 days, can be revoked, are hashed at rest and appear once on creation. Every request checks expiry, current account status, membership/grants and endpoint scope. Restore/drill additionally require `workloads:restore`; `workloads:operate` alone is insufficient. A shared administrator sign-in with no individual email must first become a verified individual account before creating these keys. A verified legacy account whose ID is still `bootstrap` is supported. The instance administrator recovery token remains separate and is not accepted by MCP.

The existing `cove` executable now also supplies client commands; **no arguments still start the control plane**, and the original `cove connect` tunnel client remains supported. Build with `go build -o bin/cove ./cmd/cove`. Client usage (replace identifiers and origin):

```sh
cove login --name home --url https://panel.example.com --team TEAM_ID --token-stdin
cove context list
cove context use home
cove deploy --wait RESOURCE_ID
cove logs --follow RESOURCE_ID
cove exec --service web RESOURCE_ID -- printf 'hello'
cove env pull --file private.env RESOURCE_ID
cove env push --file private.env RESOURCE_ID
cove run RESOURCE_ID -- command argument
cove port-forward --service database --port 5432 --local-port 15432 RESOURCE_ID

```

Supply a pre-created scoped token through standard input from a private secret source. Named contexts are saved in the user's configuration directory under `cove/contexts.json`; `COVE_CONTEXT_FILE` overrides the path. The file contains credentials, is written atomically with owner-only permissions, and must remain in a private user directory (with appropriate ACLs on Windows). Context list output never contains tokens. All commands support `--json`; follow output is newline-delimited JSON. Put client flags before positional resource IDs, and use `--` before program arguments so program flags remain intact. `COVE_CA_FILE` optionally adds a local PEM CA bundle to system trust for private panel certificates; HTTPS verification and no-redirect policy remain enforced.

`env pull` exports saved raw values/references, while `run` explicitly requests an audited resolved environment (including available built-in metadata and the last known successful commit/release). This is Cove's configured environment, not a scrape of arbitrary container environment or Git env files. External values are fetched when that local-command environment is requested. Neither method exposes registry, SSH or provider connection credentials. `env push` merges named keys and does not deploy. CLI port-forward generates a temporary private key, requests the existing 15-minute service lease, verifies the returned worker host key, binds loopback and revokes access on exit; keys are removed locally, and ambiguous revocation still expires at the original deadline.

One-off container exec requires the `exec:run` scope and current editor access. Requests select a Compose service and optionally a replica ID; the worker verifies running container ownership from Compose project/service labels before executing an argument vector without an implicit shell. Output is at most 64 KiB, commands have at most 64 arguments/16 KiB, and the RPC waits 1–30 seconds. **A wait timeout does not guarantee termination of the in-container process**: Docker does not expose an exec-cancellation API. The result flags this explicitly; inspect the container before retrying. Calls are never automatically replayed. Active operations and concurrent command limits are enforced, audit records omit command bodies/output, and response data is not cached. Upgrade and verify workers for the `exec` capability; runtime metadata now includes actual service labels for Git-source resources too.

MCP is disabled by default. Instance administrators enable it in Settings (`GET/PUT /api/mcp`), then configure a client with `/mcp` and a pre-created scoped token. The official Go SDK provides stateless Streamable HTTP, including current protocol negotiation; cookies and the administrator recovery token are refused. Available scopes determine discovery, and every resource/tool request passes through the same versioned API authorization. Resources expose accessible projects/resources and individual resource/operation metadata. Tools queue deploy/restart and read bounded logs. Origin checks, body limits and token revocation apply per request. No OAuth authorization server or token-minting endpoint is exposed through MCP.

## Project declarations and configuration review

The canonical `cove/v1` project declaration is defined in `internal/control/project_configuration.go`. The same schema is used by project/environment exports, strict YAML/JSON import, saved draft diffs, GitOps and declaration drift. A declaration contains `api_version`, `project`, optional project `variables`/deployment `policy`, named `environments`, and resources with stable `key`, environment name, existing resource `configuration` and optional variable `bindings`. Resource configuration uses the existing workload fields, including routes, limits, hooks, file secrets and ordered Compose bundles. Placement IDs and per-key patch fields are not embedded inside resource configuration. Infrastructure credentials and backup/private-network settings remain in their dedicated workflows. Unknown fields, duplicate YAML keys and multiple documents are rejected. Input is bounded to 2 MiB, 32 environments and 128 resources.

`GET /api/projects/{id}/configuration` returns a redacted declaration and an opaque version. Configuration UI saves YAML or JSON through `POST /api/projects/{id}/configuration/drafts`, reviews field names and safe diffs, then explicitly applies a selected draft. Draft payloads are sealed; responses never return variable values, private file contents or provider credentials. Saving queues no operations. Applying checks the reviewed version again, current access, persistent placement, assigned nodes, quotas, bindings, active operations and route claims, then saves the batch transactionally. Existing live route changes use normal asynchronous route operations; applying configuration does not deploy applications. Resource node/environment moves use migration workflows. Declarations upsert named environments/resources; omission never silently deletes a running resource. There are at most 100 saved drafts per project; delete old drafts explicitly.

Project/environment shared-variable maps are patches: string values set and null removes; omission preserves. A resource's non-null environment map replaces saved variables; omission/null preserves them. Omitted routes and Compose bundles preserve the existing selection. Explicit empty bindings clear them; null preserves. Bindings use another declared resource's key, or an explicit `source_id` for an existing resource outside the declaration; the latter requires current editor access to that source. Source credentials are retained only for the same repository and are never exported. Provider-managed repository changes require disconnecting that provider; SSH repository/pin changes require deploy-key rotation. Deployment policy changes additionally require team administration. The versioned API adds `configuration:write` for declaration/draft/GitOps mutations; grants are still checked by the real handlers.

`POST /api/projects/{id}/configuration/export` is an explicit audited secret read, currently requiring editor access (map this to the auth track's secret-read permission when integrating). Its optional `environment_id` selects one persistent environment. The private ZIP contains `cove.yaml`, per-resource plain Compose files and resolved `.env` files, with mode0600 and `Cache-Control: no-store`. Provider credentials/deploy private keys never leave their sealed stores. Git source files are fetched through the worker at the exported pinned revision; the archive records that source. Build contexts, included files and repository env_file assets still require that repository working tree, as `export.json` explains. Inline ancillary files are included. An inline `.env` asset is merged with saved Cove variables taking precedence. Export resolves saved shared/external references and known built-ins, without starting/stopping containers. Missing references or failed audit stop disclosure. Archives are bounded to 16 MiB uncompressed content and the manifest limit; export large projects one environment at a time. Protect downloaded archives as secrets.

Environment comparison requires read access to both persistent environments. It matches resources by unique name and returns changed field names, safe non-secret diffs and deployed revisions; shared-variable values remain hidden. Duplicate resource names in an environment must be disambiguated before comparing.

Resource deploy review reads `/api/workloads/{id}/configuration-diff`. A separate sealed `operations.declared_payload` captures the original queued declaration before Git credentials and variable resolution change the worker payload. Comparisons follow retained rollback targets. Historical operations without that declaration have an explicitly unavailable baseline; Cove does not infer that their configuration is unchanged.

### GitOps

A project's GitOps setting references an existing persistent Git resource in that project and a repository-relative `cove.yaml` path. Sync fetches that file through the same pinned Git credentials/host-key flow, parses the canonical schema and stages a redacted diff. Default manual mode requires explicit Apply. ### Runtime drift

Workers with the `drift` capability record a private runtime baseline after successful Cove service operations. Inspection compares current Docker container membership, image, container/host configuration, mounts, network membership/aliases and running state against that recorded baseline. Only service/container identifiers and changed category names return to the panel; configuration values and fingerprints stay on the worker. Changing restart policy or stopping a container manually is detected. Intentional successful Cove operations refresh the baseline; drift does not attribute a cause or automatically repair anything. A busy resource is deferred, not reported clean. Old deployments without a baseline are explicitly unknown until a successful operation records one. Inspection is bounded to 128 containers and 2 MiB of Docker metadata per resource. If baseline capture fails after an otherwise completed operation, inspect the resource before retrying.

`COVE_DRIFT_DOCKER=1 go test ./internal/worker -run TestRuntimeDriftDockerAcceptance -count=1 -v` uses one uniquely labelled local container, changes only its restart policy/running state, and removes that owned fixture and its anonymous volumes. ## Migration and adoption

### Reviewed resource moves

Both placements require editor access; cross-team moves also require owner/admin access on both teams. A personal scoped API key can transfer only under its creator's current grants; a team key cannot transfer outside its team. The old placement PUT now validates the destination and refuses changes with a pointer to the reviewed flow.

Moves retain IDs, containers, local secrets, routes and full operation history without deploying. Destination grants, shared variables, built-ins and deployment policies govern future access/deployments; source grants are not copied. Remove preview dependencies, GitOps ownership, deployment sequences, variable bindings and private/shared networks first. Materialize shared references explicitly before moving. Other build packs and standalone database API objects do not contain a portable Compose declaration and are rejected; inspect their running Compose project through node adoption when available, or supply a separately reviewed built-image declaration. Flatten include/extends, build contexts, env_file/label_file and file-backed secrets/configs first. Declare physical volume names and verified absolute bind paths explicitly. Supply every interpolation variable, including those with defaults, so worker environment credentials cannot be inherited. Literal `{{...}}` strings cannot be represented by this import's Cove variable model and are refused. All profiles are included. Custom Compose environment-file selections require a flattened source definition; process-environment-backed configs/secrets cannot be recovered from container metadata and must be preserved explicitly first. No containers are restarted or recreated during adoption; original mounts, networks, ports, files and proxy middleware remain unchanged. Cove retains image tags and a private release/ownership snapshot.

The `/api/nodes/{id}/adoptions` endpoints support discovery, planning, review, explicit adopt, refresh and recovery. Versioned callers require the `migration:adopt` scope on a personal token whose creator is an instance admin. Pending resources report `pending_adoption_id` and read-only permissions. Retry the same pending adoption after a lost reply; completed worker ownership is idempotent. Explicit Refresh reconciles that ownership and re-reviews only unregistered sources before another confirmation. A stale unstarted destination requires a new plan. Normal resource operations remain blocked until the whole adoption completes.

A matching creation hash does not detect all pre-existing manual Docker overrides: inspect them before adopting, since the initial drift baseline accepts current runtime state. The first later Cove deploy may recreate containers. Configure routes, authentication, backups and Git sources separately and follow the operator's internal same-host migration runbook for any proxy/data cutover. There is no automatic return to the source manager; normal Cove deletion requires stopped resources and removes containers while retaining volumes. Keep source automation paused until an explicit, verified ownership transition.

Native Compose import round trips run without containers. `COVE_ADOPTION_DOCKER=1 go test ./internal/worker -run TestComposeAdoptionDockerAcceptance -count=1 -v` creates only one uniquely named local Compose fixture, filters discovery to that fixture, proves IDs/start times unchanged through adoption, verifies ownership after worker restart and exercises stop/start before removing its own container, anonymous volumes and retention tag. This is not real Coolify, remote Linux or staging migration acceptance.

## Security hardening

Panel access is configured in Settings ? Panel access. Entries are literal IPv4/IPv6 addresses or CIDRs (at most 128). Empty means unrestricted network access; authentication is still required. Saving a nonempty list must include the client address the control plane sees. The restriction covers the dashboard, authentication routes and API. Health GET, worker installer/binary/update GET routes, bootstrap registration POST and signed GitHub webhook POST routes are exempt so enrollment, monitoring and webhook delivery continue; their existing credential/signature checks remain in force. Query failures and invalid configuration fail closed.

Forwarded addresses are ignored by default. Set `COVE_TRUSTED_PROXIES` to comma-separated IPs/CIDRs of the actual reverse proxies, including the proxy's Docker-network address when applicable. Only those peers may supply `X-Forwarded-For`; the chain is traversed from the right to the first untrusted hop. Do not trust a whole LAN or Docker address pool if other clients can reach the API from it. Keep port 8080 unexposed and restrict proxy access to the panel container. Test the displayed client address from an allowed and a denied client before relying on the restriction. The default Compose configuration intentionally does not trust arbitrary container peers.

**Recovery requires host access.** For a direct binary or systemd service, explicitly set `COVE_PANEL_ALLOWLIST=` (an empty, present environment variable), restart the control plane, repair the saved list, then remove the override and restart again. For Compose, add `COVE_PANEL_ALLOWLIST: ""` under `services.cove.environment` in a private override file, start with that override, repair the list, remove the override, and recreate only the panel. Alternatively, from the installation directory run `docker compose exec -T database psql -U cove -d cove -v ON_ERROR_STOP=1 -c "UPDATE control_settings SET panel_allowlist='{}' WHERE id=1"`; this resets only the network restriction, takes effect on the next request and preserves authentication. Back up the installation before changing host configuration. The UI reports an active environment override. Never remove authentication to recover network access.

For a private-network installation, `sh scripts/configure.sh cove.example.com "" 100.100.100.10` writes `COVE_BIND_ADDRESS` and binds the Compose proxy's ports 80/443 only to that IPv4 address. Use the host's actual Tailscale/WireGuard address, ensure the VPN interface is up before starting Compose, restrict host firewall access and supply DNS resolving to that address. The direct API defaults to loopback; keep it there or set `COVE_LISTEN` to the intended private address behind a trusted HTTPS proxy. Binding alone does not provision private TLS: the default HTTP ACME challenge needs public reachability. Provide a valid certificate using the existing proxy configuration or a separately managed private HTTPS ingress before first-user setup. Public worker bootstraps must still reach the private HTTPS origin through the VPN. This mode does not make workload-published ports private.

Preflight warns when resolved Compose publishes on every host interface. Runtime lists also flag Docker bindings on `0.0.0.0`/`::`; an empty runtime list does not establish firewall safety or absence of non-Docker listeners. Resource Networking offers a preview and explicit confirmation to rewrite wildcard bindings to loopback or a chosen unicast address. It preserves specific existing bindings, rejects unresolved interpolation and YAML aliases/merges, checks the saved revision and refuses edits during active operations. Git-file Compose must be changed in its repository. Saving does not alter running containers: deploy separately and verify reachability before removing an old ingress path.

The security checklist evaluates stored authentication policy/enrollment, registration, effective panel allowlist, HTTPS origin, node check freshness, scoped-token expiry and audit export/retention, plus the timestamped backup/update/runtime observations described below. A pass is scoped to the stated condition, not a security certification.

### Outbound proxy and host integration

Settings > Outbound proxy stores HTTP(S) proxy origins and NO_PROXY in the panel's encrypted settings. Credentials may be embedded in a new proxy URL; API reads remove them and report only whether they are set. Omitting a URL on update preserves it, including credentials; explicitly clearing it removes it. Standard upper/lowercase HTTP_PROXY, HTTPS_PROXY and NO_PROXY are used until an instance setting is saved. Compose forwards uppercase host values to the panel. Restart after changing host environment variables. NO_PROXY supports `*`, IPs, CIDRs, optional ports, domain suffixes and leading-dot subdomain matches; loopback and localhost always bypass the proxy.

Panel provider, Git metadata, registry and update HTTP requests use the configured proxy. Public webhook/audit destinations are resolved and validated locally before connecting; the proxy receives a CONNECT to the validated destination IP, preserving the destination Host and TLS identity. The proxy must permit CONNECT, including port80 for any HTTP traffic. Private/special-use webhook destinations stay forbidden, even through a proxy. Proxy TLS is verified normally. Workers advertise proxy support in their verification probe before receiving authenticated settings through subsequent RPCs. Git and manifest commands, including release-history fetches, use the saved settings; worker updaters read the private worker settings file. Until an instance proxy is selected or settings are explicitly saved, a worker keeps its own standard environment variables. Explicitly saving empty proxy settings clears worker overrides. Older workers keep probes and read-only inspection available, while proxy-dependent operations require an upgraded, verified worker. Initial bootstrap itself uses the operator's standard environment variables.

Image pulls execute in dockerd, outside the Docker client's proxy environment. Preflight explicitly reports this boundary whenever a proxy is selected. During an operator-approved maintenance window run `sudo python3 scripts/configure-docker-proxy.py --apply` on the worker after it has received settings. This validates and merges only the proxy section into daemon.json and preserves a private `daemon.json.cove-before-proxy` recovery copy. It does not restart Docker. Schedule the restart explicitly and verify workload continuity separately; do not change daemon-wide proxy settings on a shared worker without coordinating its other workloads. The panel host's dockerd needs equivalent host settings for registry pulls. Host updater commands fetch settings with the host administrator token and report verified channel observations; browser sessions cannot retrieve credential-bearing proxy configuration. The host updater uses COVE_PUBLIC_URL and remains subject to the panel allowlist: include its observed source address when restricting access, and include the private panel hostname in NO_PROXY when it must remain directly reachable. The updater never bypasses these controls.

### Offline distribution

On a connected, trusted build machine with Docker/Compose, Python3, OpenSSL and a trusted Cosign v3+, create an operator signing key outside the destination (for example `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out /private/cove-bundle-key.pem`). Protect that key; never include it in a bundle. Run `python3 scripts/offline-bundle.py create --version vX.Y.Z --bundle /exports/cove-vX.Y.Z --signing-key /private/cove-bundle-key.pem`. The exporter verifies official release image signatures, saves all panel/worker/database/proxy images, copies both supported worker architectures and their signature bundles, preserves upstream image signatures and Sigstore trust material, and signs a manifest covering every payload checksum. It prints the shipped trust root's SHA-256 public-key fingerprint. Deliver that fingerprint through an independent trusted channel; accepting a fingerprint from the same untrusted bundle would not authenticate it.

On the disconnected Linux host, preinstall Docker/Compose, Python3 and OpenSSL. Use a trusted copy of this verifier, then run `python3 scripts/offline-bundle.py verify --bundle /media/cove-vX.Y.Z --trust-fingerprint EXPECTED_SHA256`. Install with the same arguments and `install --installation /opt/cove --domain cove.internal.example --bind-address 100.100.100.10 --tls-certificate /private/panel.crt --tls-key /private/panel.key`. Supply a valid, unexpired hostname certificate and matching key from your private/public PKI; the offline path never requests ACME certificates. Configure private DNS and client trust separately. It loads only verified local images and starts Compose with `--pull never --no-build`; no Internet update timer is installed. Installation refuses an existing directory. Worker binaries/signatures are under the bundle's binaries directory, and the worker image is imported for local-worker use. Keep node enrollment and host prerequisites separate from Internet package installation.

Update with `python3 scripts/offline-bundle.py update --bundle /media/cove-vX.Y.Z --trust-fingerprint EXPECTED_SHA256 --installation /opt/cove`. It verifies before importing, uses immutable local image IDs, retains the normal database/configuration recovery and worker-drain checks, and persists the offline image pins after success. Existing database/proxy versions and private TLS settings are preserved. No registry, Sigstore or panel HTTPS call is required by this update path. Signatures authenticate the exporter's verified bundle; they do not prove an upstream database/proxy image is vulnerability-free. Test updates and restores on your infrastructure, and retain the independent encryption key and backups.

The security checklist now evaluates a successful encrypted backup receipt within48hours, a verified host update-channel observation within2hours, worker binary hashes from probes within15minutes, and all workloads' Docker publications inspected within15minutes. Missing/stale observations warn. The fleet scanner processes at most8workloads per pass, so larger or disconnected fleets take longer to become fully observed. Backup receipts prove the encrypted repository read-data check succeeded; offsite replication and restore acceptance remain separate.

An offline export targets one image platform (`--platform linux/amd64`, the default, or `--platform linux/arm64`) and includes worker executables for both. The importer rejects a Docker-host architecture mismatch. Add `--local-worker` to offline installation to start the bundled local worker with immutable image pins. For a disconnected remote systemd worker, preinstall its documented Linux/Docker/Compose/Buildx/OpenSSH/Git/jq/curl/Cosign prerequisites, then run the verified bundle's `trust-worker` command with the independent fingerprint. This installs only the shipped, authenticated Sigstore trust material and refuses to overwrite an existing root. Run the private panel's generated enrollment command with `COVE_OFFLINE=1`; it reaches only the panel over your private network, refuses package installation, and verifies signatures offline against the installed root. Maintain private HTTPS trust and SSH reachability independently. The offline bundle does not contain your enrollment tokens or TLS private keys.

## Release governance

### Panel channel changes and downgrades

The host updater verifies both available channel images and reports their signed version, revision, schema fingerprint and source lineage. Settings shows these observations; channel changes require a successful observation within two hours. Stable-to-stable order uses numeric semantic versions. Beta comparisons use the signed main-line source generation and root from the release workflow, rather than assuming commit dates are monotonic. Identical revisions are the same source; missing or incomparable lineage blocks automatic replacement. Release publication checks out full history to record this metadata. A history rewrite needs an explicit backed-up recovery/adoption procedure rather than an automatic inferred downgrade.

A downgrade requires the reviewed target revision and explicit confirmation in Settings. The host updater consumes that consent only for that exact observed version/revision, and rechecks actual image labels before replacing anything. Explicit CLI and offline downgrades require `--confirm-downgrade`. Every downgrade must have the same schema fingerprint as the installed image; a missing/different fingerprint blocks it even when confirmed. This is deliberately conservative: even a text-only schema change may prevent downgrade. It does not reverse application or workload data migrations.

Deploy the metadata-aware signed image before adopting the new updater on an older installation. Legacy/missing beta comparison metadata fails closed; use a backed-up manual forward upgrade, then reinstall the host update timer script. The initial installer reports verified image metadata before selecting its channel. A failed panel replacement with a different schema fingerprint stops the panel and refuses automatic startup of an older binary against the potentially upgraded database. Recovery files remain in `.cove-updates/`: preserve the dump, resolved Compose configuration, environment and original encryption key; explicitly restore a compatible database/configuration before starting an older image. Same-schema failed updates retain the existing image rollback path. Test this recovery on staging before rollout.

### Workload release comparisons and reasons

A resource's release history can compare any two successful retained releases. Configuration is reported only as changed/unchanged field indicators, including per-variable names and credential changes; secret values and raw Compose are never included. Effective variable changes also come from retained worker snapshots, so a shared secret rotation is visible even when its saved reference is unchanged. Image comparisons come from actual retained worker snapshots. Rollback configuration follows its referenced release rather than incorrectly comparing the current editor configuration. Git comparisons show pinned source/target revisions and up to100 commits reachable from the target but not the source. A bounded,30second metadata-only repository fetch may complete shallow history; it does not check out files or start workloads. Unavailable credentials/history, shallow data or truncation are clearly reported as incomplete. Pruned release snapshots cannot be compared. History comparisons are serialized per worker without reserving a deployment slot; a concurrently pruned snapshot is reported as unavailable rather than blocking deployment.

Deploy, rollback, promotion and deployment-sequence requests accept an optional `reason` of at most1000bytes. It is stored on each operation and in an atomic audit event, and appears in operation history/detail. Reasons are ordinary audit text: do not put credentials or secret values in them. Automated triggers may leave the reason empty.

### Change windows, freezes and emergency recovery

Team administrators configure deployment policy at team, project and environment scopes. All matching policies apply together. Existing daily window fields remain supported and default to UTC. An explicit IANA timezone applies to wall-clock windows; embedded timezone data makes this work in minimal images. Recurring windows select weekdays 0 (Sunday) through 6 (Saturday), start-inclusive/end-exclusive local HH:MM times; overnight windows belong to their starting day. Repeated autumn DST wall-clock hours both match, while skipped spring times never occur. A legacy daily bound and recurring windows both apply if both are configured. An empty schedule allows every time. Each policy supports up to32 recurring windows and32 absolute one-off freezes, plus the existing single freeze pair.

Outside a window, the policy either blocks or requires a team administrator's explicit operation approval. A freeze blocks until its end. Team, project and environment restrictions intersect; approval does not bypass a blocking window or freeze. A queued deploy/rollback can receive a team-administrator-only emergency override with a required reason. That action is atomic with its audit event, records actor/time/reason on the operation, and permits that exact operation to bypass schedule/approval gates. It does not bypass dependency ordering, quotas, resource locks, cancellation, authorization or worker safety checks. An admitted/running/cancelled operation cannot receive a new override.

Manual deploys/rollbacks, signed webhook deploys, sequences, promotions and both preview deployment paths all pass through the same central admission gate. Preview admission resolves its source/base environment, so creating a temporary environment does not evade source freezes, change windows or approval policy. Already admitted operations and reconciliation are not interrupted by later policy edits. Stop/start/restart, route-only changes, backups/restores/drills, preview data preparation/removal, source/image preparation, node maintenance and panel/worker updates are exempt because these are recovery, data, routing or infrastructure operations rather than new workload release admission. Existing preview-data approval and authorization still apply to those preparation steps.

## Template catalogue

The control plane serves built-in, instance-repository and selected-team templates through `GET /api/templates`. The dashboard has no bundled fallback catalogue. Definitions and upstream installation/licence links live in [the built-in index](../internal/catalog/builtin.json). Image versions are explicit tags or SHA-256 digests; updates to templates do not update existing resources. A template creates a reviewable configuration, never an automatic deployment. Check preflight on the intended worker before deploying.

An index is one JSON object with `schema_version: 1` and `templates` (1–250 definitions, at most 8 MiB). Each definition has its own `schema_version: 1`, unique lowercase `id`, `name`, `description`, `category`, HTTPS `source`, `license` and `docs` links, `images` mapping service names to pinned references, self-contained `compose`, `variables`, optional `web`, `storage`, `backup`, `minimum`, `notes`, `capabilities` and optional runtime `file_secrets`. The built-in index is a complete format example. Unknown JSON fields and unsupported versions are rejected. Minimum CPU/memory/disk hints are starter sizing floors, not workload-capacity guarantees. The licence link describes upstream terms; dependencies in an image may have additional licences.

Variables have `key`, `label`, `type`, `default`, `required` and `generated`. Types are `string`, `secret`, `integer`, `boolean`, `hostname`, `url` (HTTPS) and `email`. Secret defaults are forbidden. Generated secrets are 32 cryptographically random bytes encoded as 64 lowercase hexadecimal characters; replacements must use the same safe encoding, including when interpolated into connection URLs. Secrets are generated on each draft request, not stored in catalogue metadata. An exported template instead requires fresh manual values, since replacing an arbitrary command or setting with random text would change its meaning. Ordinary Compose interpolation uses declared variables; double dollars retain Compose's container-side expansion. `web` contains `service`, `port`, `route` and `url_variable`: only `route: true` creates an HTTPS route and derives the URL variable from the supplied hostname. Internal service ports do not become host publications or public routes.

Validation uses the official Compose schema/loader and the existing worker request, route, environment and file-secret validation. Templates cannot read local files, include other Compose files, build images, run lifecycle hooks, name fixed containers or attach external resources. Persistent mounts use named resource-scoped volumes. Privileged containers, host namespaces, host binds, Docker/Podman sockets, devices, added capabilities and security options require explicit `capabilities` declarations and acknowledgement in the dashboard before generating a draft. Mount sources and host namespace choices cannot be parameterized. Declared access remains powerful: a read-only Docker socket still permits Docker API operations. Dozzle is intentionally internal and carries this warning. Templates without upstream authentication, including telemetry endpoints and administration tools, do not receive automatic public routes. Applications with a first-user wizard must be claimed privately before public use; notes call out upstream default accounts and required initialization.

Instance administrators manage sources in Settings; team owners/admins manage their team's sources. A source is a public HTTPS index URL or Git repository with an explicit branch/tag/commit reference and a `cove-templates.json` file at its root. Up to eight sources are allowed per scope. Credentials, URL query strings, non-443 ports, redirects and private destinations are refused. These imports use the existing outbound proxy and validate the final destination's resolved addresses before connecting, including through a proxy. Git is fetched without checkout, hooks, submodules or repository scripts, with time, file and pack-size bounds. Private repositories are deliberately not a catalogue credential store.

New sources are scheduled immediately; the background loop checks every minute and refreshes each source every six hours. Git sources require Git on the control-plane host; the packaged panel includes it. A successful refresh atomically replaces the validated snapshot and pins its Git commit or index SHA-256. A failed refresh retains the last valid snapshot, records the failure, and adds a catalogue warning. A source without a valid snapshot offers nothing. Add, remove and refresh are audited. Draft requests include the reviewed revision; changes require another review. Removing a source or team template does not affect existing resources.

Team owners/admins with edit access can **Save as template** from a resource. Preview returns only sanitized configuration, then confirmation saves it to the team. All previous environment, command, health-command and inline configuration values become required secret variables with no defaults. Existing environment values and Git access tokens are never copied. Runtime file-secret mappings are retained without values. Host ports and integration labels are removed; routes become internal port hints. Pinned images are required. Host mounts, external files/resources, hooks, private-access policy, jobs or unsupported fields require a reviewed repository template rather than silently losing behavior. Git-backed exports fetch the configured public HTTPS file using the source's existing credentials, and pin its revision between preview and confirmation. Preview-managed resources retain their normal mutation restriction. A changed configuration or source revision refuses confirmation.

Run `go test ./internal/catalog` for all built-ins against the format and Compose safety rules. `python scripts/test-template-catalogue.py` also runs actual `docker compose config` for every entry. `python scripts/test-template-catalogue.py --start all --timeout 180` pulls pinned images and starts each stack sequentially on its own internal network without published ports. `--start postgres pgweb` selects a smaller runtime set. The runner requires a preloaded `python:3.12-alpine` readiness client (`--client-image` can select another compatible local image); it does not install dependencies into application containers. Each fixture has a unique `cove-catalogue-*` project and removes only its own containers, networks and volumes. Host-access templates are skipped on a shared daemon and need a dedicated acceptance worker. No staging host is involved.

Timestamped config/runtime results and the exact Compose hashes are recorded in [validation.json](../internal/catalog/validation.json) and shown in the catalogue. `started_healthy` means the isolated local stack reached running/healthy state and its HTTP endpoint responded where applicable; it does not establish application workflow, mail, OAuth, public TLS, ARM64 or production-capacity acceptance. `config_only` is explicitly distinct. Evidence for a changed Compose hash is not reused. The harness stores no application logs or generated credentials in the evidence. See the dated handoff for this revision's environment, failures and remaining acceptance.

## Trust and integration merge boundaries

API token scopes are an upper bound on the creator's current catalogue permissions; they never replace the per-target check. Resource permission metadata includes the exact catalogue plus the existing read/edit aliases. read_secrets is independent of edit_configuration: saved-variable/Compose/project exports and preview credentials require it, resource binding sources require it, and exec requires both. An environment-only secret grant permits exporting that selected environment, not other environments. Safe draft metadata requires configuration editing rather than a secret read. The instance recovery token retains its explicit break-glass exemption; session/account introspection and factor-enrollment recovery remain available under enrollment policy. MCP initialization, token operations, hook creators and background GitOps apply normal account-policy checks. Public status links stay anonymous, token-scoped and subject to the panel allowlist. Signed provider webhook POSTs retain the existing GitHub network-policy exemption, including the other signed Git providers; deploy hooks are not exempt from the allowlist.

All actual deploy/rollback requests, including hooks, tags/releases, CLI/API/MCP and bulk requests, use the common admission gate. ### Mount capacity, scheduled cleanup and journal retention

Linux probes report every mount visible in the worker mount namespace, with filesystem type and statfs capacity. Pseudo filesystems without capacity are identified separately from failed measurements. The response is bounded to 2,048 distinct mount paths and 256 KiB of path text; clipping is explicit. Native workers see host mounts; containerized workers see their container namespace. Historical mount samples use separate series under existing global telemetry caps. Disk rules preserve the original Cove-data-filesystem behavior when `mount_path` is empty; an absolute path selects that mount and `*` selects the fullest measured mount. Missing/failed readings never recover an alert, and a clipped all-mount scan cannot recover unless its measurements establish a failure. Team administrators can inspect assigned-node mount readings through `/api/notifications/mounts?node_id=...`; instance administrators also see them on node details.

Instance administrators configure worker cleanup through node `cleanup-policy`, `cleanup-plan` and `cleanup-run` endpoints. Defaults remain a six-hour schedule and 168-hour minimum age, with owned unused/dangling images and Cove's dedicated build cache enabled. Volumes and non-Cove images/volumes require separate explicit opt-ins. Cleanup never removes containers or uses forced image/volume deletion. It skips images used by any container, all retained-release image tags, volumes referenced by stopped containers, every volume of a recorded workload, and protected Cove ingress/link/builder storage. Recreating a deleted workload is not a way to recover a removed orphan volume.

Preview lists exact resource identities, estimated known bytes, unknown volume/cache sizes and cache records skipped because their age is unknown. Image/shared-layer sizes are estimates rather than guaranteed physical reclamation. Minimum image age uses the newer creation/last-tag timestamp, protecting fresh imports with reproducible build timestamps. Buildx versions that emit human-readable JSON sizes and dates are parsed conservatively; approximate or unknown last-use ages are excluded. Apply re-previews and requires the same revision. The scheduled loop runs only while no worker operation or recovery is pending, and an active maintenance guard prevents dispatch and upgrade from overlapping removal. Only one bounded policy/last-result record is stored per worker. Errors stop the pass and remain visible; scheduled retries use the configured interval.

Global operation retention defaults to 90 days/100,000 panel rows, configurable alongside telemetry and audit retention. A bounded periodic pass processes up to eight ready nodes and 500 candidates per node. It excludes unfinished operations, prerequisite dependencies, pending deliveries and webhook references; the worker additionally protects all retained release states, current deployments, backups, recovery metadata and references in unfinished journals. The panel deletes only worker-acknowledged IDs, and an acknowledgement lost after deletion is safe to retry. Protected records can exceed the configured count or age: these limits apply to eligible history and do not override recovery safety. `/api/settings/operation-retention` reports the last pass, errors and protected/pruned counts per node; its run endpoint starts another bounded pass. Offline, older or busy workers defer pruning visibly rather than losing reconciliation state. One status row per node is retained, with no growing run history.

### Filesystem-backed volume backups

Volume backup policies optionally set `volume_snapshot: {max_bytes: 1073741824}`. Omitting it keeps the stopped method. `max_bytes` is traditional LVM copy-on-write space (default 1 GiB, allowed 64 MiB–64 GiB), not a dump-size limit. Logical database policies cannot enable it. Workers must advertise `filesystem_snapshots`; `GET /api/workloads/{id}/backups/snapshot-preview?max_bytes=1073741824` inspects deployed writable mounts without creating snapshots. Protocol support does not guarantee host filesystem support. Actual backups re-inspect, and records report `volume_method` and an optional `fallback_reason`.

Supported sources are dedicated Btrfs subvolumes without nested subvolumes, mounted ZFS datasets and traditional ext4/XFS LVM logical volumes. Thin LVM volumes, top-level Btrfs roots, missing tools, insufficient LVM space and hosts without a working systemd manager use the stopped method. Cove does not install storage tools or create pools/volume groups. The LVM group needs the configured COW space plus 256 MiB spare. Containers pause briefly, host writes are synchronized, then atomic filesystem snapshots are created and the original running containers unpause before restic reads the read-only data. Database transaction consistency still needs the engine's logical backup or PITR method. Restore always keeps the existing stopped/safety-snapshot behavior.

The worker uses a restricted local helper in the host mount namespace, including when the worker is packaged in Docker. Its private executable cache is capped at 64 MiB. A snapshot session has at most 16 mounts and a 35-minute lease, with at most 16 indexed sessions per worker. Its bounded recovery JSON resides under `workloads/<id>/filesystem-snapshot.json`, so operation retention preserves its references. Owner nonces, exact names/properties/LVM tags and fixed private mount paths constrain deletion. Host systemd units inspect expired sessions every 30 seconds and after boot; worker startup force-cleans unfinished sessions before accepting RPC. Cleanup unpauses only the original owned containers and never starts stopped ones. A failed cleanup retains the journal and blocks removal/other operations for repair; restarting the worker retries recovery. LVM overflow or missing snapshots fail publication and leave encrypted snapshot cleanup under the existing repository journal.

Run `COVE_TEST_FILESYSTEM_SNAPSHOTS=1 COVE_TEST_WORKER_BINARY=/absolute/path/cove-worker go test -v ./internal/worker -run TestFilesystemSnapshot -count=1 -timeout 40m` only as root on a disposable Linux host with Docker, systemd, Btrfs/LVM/ZFS tools and matching kernel modules. It creates owned loopback filesystems and tests encrypted backup, exact restore, worker recovery and independent host recovery. It must not run on staging or a production storage host. Kernel/host-specific acceptance remains separate from unsupported-filesystem fallback tests in the packaged browser fixture.

### Worker SSH reachability and identity

Instance administrators manage up to 32 single-hop bastions through `/api/bastions` and select one through `/api/nodes/{id}/bastion`. Creation requires an independently obtained SSH host public key, endpoint and dedicated Linux login. Cove generates and seals a separate authentication key; only its public key and host fingerprint are returned. Worker addresses resolve at the bastion, and both SSH host pins are checked. No agent forwarding, password login, unpinned fallback or general worker shell is introduced. Native RPC and binary transfers use the same hop.

Configure the dedicated bastion account outside Cove before verification. Restrict its server-side `Match User` to `AllowTcpForwarding local`, exact `PermitOpen` worker host/port destinations, `AllowStreamLocalForwarding no`, `AllowAgentForwarding no`, `X11Forwarding no`, `PermitTTY no` and `ForceCommand /bin/false`. Use the generated public key with `restrict,port-forwarding`, matching `permitopen` restrictions and a false forced command. The key options alone do not refuse remote forwarding; server-side local-only forwarding is required. An empty destination set must allow none, never a wildcard. The API lists at most 256 destinations per bastion and reports truncation. Deletion requires detaching nodes first. Selecting a bastion resets verification state; use the existing Verify action. The worker's normal `cove` key remains restricted to its forced RPC command.

Workers advertising `ssh_identity` support resumable authentication-key rotation through `GET/POST /api/nodes/{id}/identity`. Confirmed actions are `rotate`, `retry` and `cancel`. The panel stages a second restricted key, verifies fresh SSH plus protocol RPC, transactionally stores the encrypted new identity, then confirms old-key removal. States are queued, staged, switched, aborting and terminal succeeded/cancelled; switched identities cannot be cancelled because the new identity is already saved. Pending steps retry at most once a minute; explicit Retry makes the next attempt due. Enrollment renewal and fresh installer fetches are refused during rotation. A successful/cancelled result removes duplicate sealed key material; one last result per node remains. Worker storage is one public-key journal plus one fixed 64 KiB staging file, with ownership and replay checks. Other authorized keys and their restrictions are preserved. Transport failures keep the intent pending; they do not prove cancellation or old-key removal.

Confirmed worker or bastion host-key mismatches refuse connections, preserve saved pins and expose public fingerprints in node SSH status. `host_key_changed.alert` and `.recovered` use existing assigned-team confirmation/repeat routing. Generic network failures leave a prior mismatch active; a successful pinned connection clears it. Reconcile changed host identities through a trusted console rather than accepting a network observation automatically.

`python scripts/test-node-ssh.py` builds uniquely tagged disposable PostgreSQL/OpenSSH fixtures without a Docker socket or shared ingress. It exercises actual two-hop RPC, both host pins, refused worker shell/remote forwarding/unlisted destinations, alert/recovery, lost key-change receipts, worker restart, staged cancellation and replay refusal, encrypted state cleanup and repair after the authorized-key file is reverted during the switch. A Docker restart can reassign an automatically published host port; the fixture reads back the new mapping. Native tests verify cancellation of an SSH handshake over a forwarded channel. Real bastion accounts, host key changes, connection loss and system SSH/SELinux policies still need coordinated staging acceptance.

### PostgreSQL point-in-time recovery

The resource Backups page configures PITR independently of normal snapshots. `GET/PUT/DELETE /api/workloads/{id}/pitr`, `POST /api/workloads/{id}/pitr/backup` and `POST /api/workloads/{id}/pitr/restore-copy` require resource read for inspection and edit for changes, with normal audit and preview protections. Workers advertise `postgres_pitr` on Linux amd64/arm64. A normal backup storage policy is required first; PITR uses a separate prefix and independent sealed key in that configured location, or a separate local Docker volume. Legacy inline S3 locations must be replaced by configured storage connections. Saved credentials are never returned. Credential rotation is allowed for the same destination after rechecking its archive owner marker; moving the archive or selecting another service requires explicitly deleting disabled history first.

Sources must be dedicated writable PostgreSQL 15–18 primaries with administrator credentials in standard `POSTGRES_*` or `_FILE` values, local `/var/run/postgresql` access on port 5432, a persistent named data volume, internal configuration files, standard 16 MiB WAL, no external tablespaces or other replication slots, replica/logical WAL level and no pre-existing archiver. The first enable and disable need confirmed PostgreSQL restarts to add/remove a private Unix socket. Later capture and base backups are online. Deploy, rollback and in-place restore require disabling capture first; retained history remains available. Unsupported source layouts fail before changing PostgreSQL settings. External changes to settings/cluster/storage require reconciliation rather than silent replacement.

The worker pins WAL-G 3.0.10 by release checksum, reuses rclone 1.76.0 and stores neither tool inside the application image. Its read-only helper has a 1 GiB memory limit, bounded executable/temporary filesystems and an authenticated loopback S3 bridge over the existing verified storage transport. Policies allow 1–168 hours between bases, 1–32 retained bases, 1–30 days and 1–64 GiB of encrypted archive bytes. At most 32 resources per worker and 256 per panel use PITR. Archive admission also caps 100,000 objects; pressure pauses capture while preserving the newest base. PostgreSQL enforces the 512 MiB replication-slot retention setting at checkpoints; this is not a cap on all PostgreSQL WAL allocation. Disable restores the original owned settings and removes only Cove's slot. A source image holder uses temporary mounts rather than creating anonymous data volumes.

The helper commits a small transaction heartbeat without changing application tables and switches WAL about once a minute. A window extends only when that commit's complete WAL segment is archived and integrity is known from the selected base. Partial segments, stale measurements, gaps and missing observations remain unknown. Newer bases can establish a new recovery span after a capture interruption. Old base integrity is refreshed in bounded rotating passes. Observed windows are not a guarantee against later storage loss or corruption; PostgreSQL must actually reach the requested timestamp before a copy succeeds. Recovery windows persist up to 32 archive/cluster-bound verified heartbeat receipts and are reverified against retained WAL at historical LSN/timeline cutoffs without connecting to the source; disabling or restarting capture preserves usable historical windows. Receipts and inventory are observations, not availability guarantees.

PITR always creates a new dedicated PostgreSQL resource in the same project/environment/node. It keeps all databases and roles, uses a retained immutable source image, fresh storage, an internal network and no published ports or routes. A 2 GiB isolated verifier replays and promotes at the chosen UTC time; a separate bootstrap resets the copied administrator's password without changing HBA, then a normal login is verified. Credentials are sealed into the new resource configuration, returned once in its creation response and never returned by later reads. Save them before closing the one-time view; the Environment page shows only their key names. The copy remains offline for review/deploy. A failed copy is blocked with its data volume retained; the source is never overwritten. Recovery needs twice the configured byte budget plus a 256 MiB reserve, has a 30-minute deadline, and conservatively checks filesystem growth/free space while fetching. Concurrent disk pressure can fail the check. Worker restart removes only ownership-verified staging helpers/volumes, preserving the copy's data and recovery references.

Deleting PITR history requires disabled capture and explicit confirmation; it removes only that owned archive, not ordinary backups or source data. Partial deletion retains retry metadata. Resource removal remains blocked until PITR history is deleted. Global operation retention preserves references in retained PITR bases and copy journals. Real acceptance tests run with `python scripts/test-database-backups.py 'TestPITR|TestBackupHelperOwner'` in disposable Docker; they include local and private-CA authenticated S3 capture, timestamp copies, normal login, idle-source windows, capture resumption, source preservation and cleanup. Full PostgreSQL/control checks use `scripts/test.ps1`. Real provider credentials, other supported PostgreSQL versions/extensions, ARM64, long outages and power loss require separately coordinated acceptance.

### Traffic, uptime, forwarding and Prometheus

Traffic logging is an explicit instance-admin node setting. Preview then apply the exact revision at `/api/nodes/{id}/traffic`; applying briefly restarts the Cove-managed proxy. The worker preserves its immutable image, configuration, networks and existing data volumes, validates ping and previously enabled routes, and retains the previous container until commit. A bounded durable journal rolls back failed replacements and resumes cleanup after restart. Pending recovery pauses deployment dispatch and remains repairable through the explicit recovery action. Remote Docker contexts, auto-remove proxies, host/shared namespaces and static container IPAM need a separately planned proxy migration; the normal local Unix Docker socket is supported. Neither an image upgrade nor a certificate reset is part of this operation.

Traefik emits JSON with only router, peer, status, response bytes, duration and forwarded-for fields. Request paths, queries, authorization and other headers are dropped. Its Docker logs rotate at 4 MiB with three files. Trusted proxy CIDRs are explicit (maximum 32, no `/0`); client IP selection trusts forwarded-for only behind those peers and walks the chain from the right. The panel collects at most 2,000 access entries per node pass, overlaps/deduplicates cursors, maps only generated Cove routers, and keeps at most 200,000 rows, 64 MiB of accounted payload and seven days globally. Resource traffic shows requests, status classes, bytes, p95 observed duration and the latest 100 sanitized access entries for hour/day/week ranges. Statistics describe retained observations; rotation, downtime and collection bounds can leave gaps.

Route uptime checks run HTTPS GET requests from the panel to a configured service hostname and a path without query/fragment. Public-address validation and DNS pinning reuse the webhook transport; redirects are not followed and response bodies are discarded. Checks support expected status ranges, intervals 60?86,400 seconds and timeouts 1?10 seconds. Limits are one per resource route, 64 per team, 256 globally and an aggregate timeout/interval scheduling budget of two. Four concurrent probes claim at most 16 checks per pass. Results retain at most the latest 500,000 sequence positions and 30 days; sequence gaps can reduce the row count. Configuration versions prevent old in-flight results overwriting edited checks. Removed routes disable their checks. Uptime threshold rules count consecutive failures with the standard per-rule confirmation, repeat, recovery and channel routing, allowing gaps appropriate to the checking interval. Disabled/deleted checks do not invent recovery events.

Public status is opt-in per project owner. A random stable slug publishes only the chosen title and explicit nonempty check labels, current/stale status, last check time/latency and observed 24-hour sample ratio. It exposes no internal IDs, target paths, raw errors or automatic domain names. Read-only public access is rate limited; disabling the project page returns 404. Missing/stale samples remain unknown, and sample ratios are not continuous uptime guarantees.

Team administrators configure up to eight sealed log forwarders: Loki JSON push, TLS syslog with octet-counted RFC 5424 framing, OTLP HTTP JSON, generic HTTP JSON, Axiom dataset ingestion and Datadog logs. The full HTTPS ingestion URL is explicit (TLS syslog requires an explicit port); receivers must resolve to public addresses with verified TLS, and redirects are refused. URLs and credentials are never returned. Blank values preserve saved fields only for an unchanged receiver kind. Newly persisted redacted logs enter a sealed outbox in batches of at most 100 entries/256 KiB; replayed stored entries are not queued again. Global bounds are 2,000 pending batches/64 MiB including accounted row allowance, six attempts and 24 hours. Overflow, expiry, disabled receivers and exhausted retries increment visible drop counters. Delivery is at least once; HTTP includes stable `X-Cove-Delivery` hashes for receiver deduplication. Syslog can partially deliver before failure. No response bodies or receiver secrets are logged. Test actions send a clearly identified synthetic message only when explicitly requested.

Instance admins generate/rotate/revoke a dedicated Prometheus token under `/api/settings/metrics-token`. It is returned once at creation; only its SHA-256 hash is stored. `GET /metrics` requires `Authorization: Bearer <token>` even when a session cookie or another API token exists. It exports panel goroutine/heap/operation-record gauges and fresh node, mount and container CPU/memory/disk/network/block measurements; samples older than five minutes or unknown values are omitted. The exporter bounds concurrent scrapes to one and output to 8 MiB/10,000 series groups and sets `cove_export_truncated` when clipped. Metric labels include internal IDs, so the token grants instance-wide metric visibility. Tokens must stay out of URLs and browser persistence.

Local verification uses `scripts/test.ps1` for disposable PostgreSQL, `go vet ./...`, `go build ./...`, and opt-in worker Docker tests. `TestProxyTrafficDocker` requires a Linux test binary in a fresh disposable Docker-in-Docker daemon with `COVE_TEST_PROXY_TRAFFIC_DOCKER=1`; it refuses an existing proxy, exercises a real HTTPS access record, preserves data, and forces replacement failure to verify rollback. Never run that test against a shared or real worker daemon. Live provider delivery, trusted reverse-proxy chains, publicly trusted certificates, restart/power-loss acceptance and production load remain staging acceptance tasks.

Docker manual stop/restart/kill events are excluded from container crash/restart observations, including commands issued outside Cove. The worker retains only the current containers' known exit stamps (at most 32/16 KiB per workload) for the workload's lifetime, so intentional stopped states do not become crashes when the recent event window expires. A first inspection of an old exit with no retained cause reports it as unknown; it neither triggers nor recovers a crash rule. Known unexpected exits remain measurable after the window. A stop caused only by arbitrary application code or a signal sent inside a container has no Docker management intent event and is observed as an application exit.

## CPU scaling

`GET|PUT /api/workloads/{id}/autoscale-policy` reads or edits a service's CPU scaling policy. PUT requires an explicit `enabled` boolean and a `services` map, for example `{"enabled":true,"services":{"app":{"min_replicas":1,"max_replicas":4,"target_cpu_percent":70}}}`. Read and edit permissions are enforced separately. Enabling requires worker capability `cpu_autoscale`, a healthy deployed rolling generation, managed HTTP routes and explicit CPU and memory limits on each selected service. Jobs and managed previews are excluded. Configure limits and a rolling replacement strategy, deploy once, then enable scaling. Policies cannot change during an active operation; disabling retains the current replica count and does not reset the attempt cooldown.

The panel samples enabled resources at most once per minute in batches of four; busy installations can take longer. Three complete samples, 30?90 seconds apart, must name the same generation and replica counts. The latest sample must be no older than 90 seconds. CPU is the average Docker CPU percentage divided by each replica's explicit CPU limit: Docker 100% represents one core. Three samples at or above the target add one replica; three at or below half the target remove one. Minimum and maximum bounds apply after the same observation gate. Every queued attempt starts a five-minute cooldown, including cancellation or failure. Unknown, unhealthy, sleeping, suspended, stopped, staged or busy resources do not scale. Missing data never counts as low CPU.

The scaler deploys the current immutable images and environment through the existing health-gated rolling replacement; it does not check out Git, rebuild or pull newer tags. Ineligible topology fails the scaling attempt rather than falling back to a disruptive replacement. The deployment remains subject to approval, freeze, time-window and team deployment-slot rules. A pending approval therefore holds the resource's operation slot. Saved replica counts change only after a successful worker result. Maximum replica counts reserve configured team CPU/memory budgets, while transient old-plus-new generation headroom remains the operator's responsibility. Stopping the panel stops CPU sampling but leaves applications and routes running.

`COVE_TEST_CPU_DOCKER=1 go test ./internal/worker -run TestCPUScalingDocker -count=1` requires an isolated Linux Docker daemon with cached `busybox:1.37` and `traefik:v3.7.19`. It measures live CPU load, scales immutable replicas up and down through real Traefik, rejects a stale generation and checks continuous HTTPS traffic. Unit/controller tests cover sample freshness, complete health/metrics, cooldown, bounds, quota reservation and approval. No request-threshold control is provided without request-rate telemetry.

Paused/asleep restores and drills are held, including restore-copy. Backup downloads and dump repository imports do not restore live data and retain their separate secret-equivalent permissions.

The public forward-auth transport validates resolved public IPs before CONNECT, verifies TLS and refuses redirects; owned-service auth stays on the worker-owned network. A saved proxy change refreshes the helper or refuses the change and restores its previous settings. Publishing and explicit pull-and-redeploy refuse a configured proxy that differs from `dockerd`'s reported HTTP/HTTPS/no-proxy configuration. Use the existing `scripts/configure-docker-proxy.py` only in an explicitly approved host maintenance window; the panel does not reconfigure the host daemon. A local fake validates that refusal and private-builder proxy propagation; real proxy/provider acceptance remains separate.

Request-rate autoscaling remains unimplemented. Operations supplies sanitized request telemetry, but a controller still needs stable logical route/service attribution across replica generations, a defined sampling/aggregation window, freshness and missing-data rules, hysteresis/cooldown and tests that avoid counting idle gateways or helper requests. The merge does not infer such a policy from traffic totals.

For the packaged harness, the constant machine-wide temporary-file lock spans build through cleanup. Per-run unique panel/worker tags and startup assertions for integration, trust, operations and deployment lifecycle contracts prevent a different worktree's binary from passing accidentally. ## Managed databases and object storage

The database resource kind uses the built-in pinned PostgreSQL, MySQL, MariaDB, MongoDB, Redis, Valkey and ClickHouse configurations. Saving generates credentials and named storage; deploy explicitly to start the engine. Generic Compose, environment, source, hooks, routes and file-secret editors are locked for this kind. Normal limits, approvals, freezes, change windows, health and backup APIs still apply. Maintenance, certificate bindings and administration tools require the `managed_databases` capability from an upgraded, verified worker.

Database resources export `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` and `DB_URL` through resource variable bindings. A binding grants no network access: create a private connection to the displayed service, native port and canonical hostname, then deploy the consumer. ClickHouse also permits private HTTP on 8123; its URL uses native port 9000. MongoDB authenticates against `admin` and creates application database `app` on first write. Redis/Valkey use ACL user `default` and database 0. Credential reads require edit and secret-read permissions and are audited. Prefer bindings to copied secrets. Clones, previews and upgrade copies start private; a clone without secrets gets fresh credentials and a new hostname.

Rotation requires explicit confirmation of the configuration revision and uses a retained worker journal. New credentials are committed to the panel only after the engine accepts them; bindings and credential reads fail closed while a password change is unresolved. Retry the same maintenance after an ambiguous SSH reply; do not queue a second rotation. Rotation can interrupt clients and does not terminate every existing authenticated session. The Database page lists bound consumers requiring a redeploy, without deploying them automatically. MySQL/MariaDB retain a separate root credential; the other templates start with an administrative account, so create separate least-privilege engine roles where appropriate.

Public access is **off by default**. Enabling it requires a matching operator-provided PEM certificate/key, DNS hostname, worker bind IP, port and confirmation. The certificate must verify against the supplied root bundle and remain valid for at least 24 hours; a self-signed certificate can be its own trust root. Private keys are sealed and delivered as worker file secrets; responses expose only the fingerprint, expiry and public CA. Only the native TLS listener is published. Manage DNS, firewall rules and certificate renewal before expiry. PostgreSQL/MySQL/MariaDB/MongoDB private clients must also use native TLS while this is enabled; Cove atomically updates canonical connection aliases to the certificate hostname. Bound consumers receive the public CA under `/run/secrets/cove_ca_<database-id>` and verified TLS parameters, but each driver needs its supported TLS options. Redis/Valkey keep private 6379 and publish TLS 6380; ClickHouse keeps private 9000/8123 and publishes TLS 9440. **Recovery:** use Database > Public access > Disable to queue the original private configuration and remove certificate material, including after a failed enable operation. Finish or retry any pending password maintenance first. A configuration change does not take effect until its normal deploy succeeds.

PostgreSQL offers `pg_trgm`, `hstore`, `uuid-ossp`, `pg_stat_statements`, pgvector and PostGIS. pg_stat_statements changes preload configuration and restarts the service. Disabling uses `RESTRICT`, never `CASCADE`; dependency preflight refuses removal before queuing. PostGIS removal includes the image-installed topology/geocoder/fuzzystrmatch companions in one transaction, and refuses any application dependency. Disabling an extension retains its image variant. pgvector uses an immutable PostgreSQL 18.7/pgvector 0.8.7 image; the pinned PostGIS image contains PostgreSQL 18.6/PostGIS 3.6.4 and supports Linux amd64 only. Its older patch version is explicitly shown. Changing image families uses a separate logical copy so libc/collation changes rebuild indexes on new storage, with the source intact. Validate application queries before cut-over.

Optional PgBouncer uses a pinned image, SCRAM authentication and private port 6432, with transaction pooling. It exports `DB_POOL_HOST`, `DB_POOL_PORT`, `DB_POOL_USER`, `DB_POOL_PASSWORD`, `DB_POOL_NAME` and `DB_POOL_URL`; create a private connection to service `pgbouncer` and the displayed pool hostname. Clients opt in by choosing these bindings. Rotation updates both native and pooled credentials. No pooler host port is published; the pooler verifies upstream TLS against the saved CA when native TLS is enabled. Remove pooled bindings/private connections before disabling it.

The copy assistant supports PostgreSQL 17.12 to 18, PostgreSQL 18 image-family copies, MySQL 8.0.46 to 8.4.13, MariaDB 10.11.19 to 11.8.9 and MongoDB 7.0.48 to 8.0.38. MySQL 8.0 is end of life and is offered only as a recovery/upgrade source. Runtime preflight verifies the source version, installed PostgreSQL extensions, target architecture and MongoDB FCV 7.0. A private safety dump and checksum must verify before starting the target; SQL copies reject nontransactional application tables. PostgreSQL checks the archive catalogue; MongoDB dry-runs the archive and restores with the same tools at matching FCV, then advances only the new copy to FCV 8.0. Only application database `app` is copied: cluster users, grants and other databases are excluded. Source volumes/configuration remain unchanged. On failure the target stops and the source becomes available again; retry the retained copy, or explicitly discard its data by typing the target name. Discarding never removes the source.

A copy is a snapshot, **not continuous replication**. Copy creation requires confirmation that application and external writers have stopped; this is essential for a consistent standalone MongoDB dump. Cove cannot stop or verify external writers. Keep writes stopped while validating the target and review snapshot freshness before a team administrator separately confirms cut-over. Confirmation atomically moves variable bindings and canonical private connections, increments connection versions and records an audit event; redeploy consumers separately. The old resource is retained even after cut-over. To roll clients back, stop writes again and deliberately restore their bindings/connections to the retained source after reviewing data divergence. Never treat an old copy as an up-to-date replica.

Temporary administration tools are Adminer for SQL, Mongo Express for MongoDB and Redis Insight for Redis/Valkey. They run on the database's managed private bridge with no host-published port, restricted capabilities and a container-side lifetime limit. Tool access requires edit and secret-read permission. Credentials travel only in the encrypted worker request/child environment, not browser URLs or command arguments; public-TLS databases receive a verified CA connection. Mongo Express also uses Basic authentication with the database credentials. Redis Insight asks for its own first-use agreement before displaying the preconfigured connection; Cove does not accept it for the operator. The authenticated SSH lease lasts 15 minutes; revocation/expiry close streams and remove the helper and its temporary data. Worker recovery removes its own orphaned helpers. Use a fresh Ed25519 key per lease, retain the private key locally and pin the worker's displayed host key. The CLI listens only on loopback and requires an SSH-enrolled worker reachable from the operator. Native-protocol tunnels remain available.

For object storage, deploy the unmodified Garage catalogue template, route HTTPS only to service `garage` port 3900, and provision a bucket from a consuming workload. The administrative API stays private. Team administrators acknowledge the same-node risk; the generated key has read/write access to one generated bucket, without ownership or bucket-creation permission. An authenticated read-only check must pass before retaining a provisioning request. Retry a pending request with its retained credentials. The consumer receives bound `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and `S3_REGION` on its next deploy. An optional S3 backup destination uses the existing backup APIs and supports a private CA through the storage editor. Same-node storage is **not offsite**; keep another copy in an independent failure domain. Revocation removes the key and bindings but retains bucket data. Move backup policies and other bindings first. No backup-engine internals are changed by these resource features.

Run `python scripts/test-browser.py --managed-data` against the owned disposable local fixture for the native engine checks. Focused cases use `COVE_MANAGED_DATA_CASES=pooler`, `tls`, `tools`, `upgrades`, `extensions`, `cache-backups` or `buckets`; `COVE_MANAGED_TLS_ENGINES=postgresql,mongodb` narrows TLS checks. Fixture panel/worker images have unique per-run tags. The runner holds the shared `cove-browser-fixture.lock` before building and through cleanup. Its managed-data subprocess requires the lock-holding parent. Cleanup proves fixture ownership for route, idle, link, database-tool and operational helpers before removal; explicit foreign owners are preserved, and a remaining `cove-ingress` network fails the run. All runtime claims must identify the actual passing case and tree; local x86_64 Docker tests do not establish production TLS/DNS/firewall, ARM64 or fleet-capacity acceptance.


### Merged managed-database boundaries

Managed databases use single-instance deployments. Replica rollouts, idle sleep, CPU scaling, unhealthy auto-restart and arbitrary Compose bundles remain unavailable. Environment pause/resume retains their containers and suppresses intentional-down alerts. Database changes and version-copy deployments follow normal approval, freeze and deployment-window admission; inspection and explicit metadata cut-over do not create a release. Unresolved maintenance records and their worker journals are retained so pruning cannot unlock uncertain credentials.

The `databases:manage` automation scope requires View, Edit configuration and Read secrets, rechecked against the creator's current grants. Database metadata bindings need View on the source; password and URL bindings need Read secrets. Destinations independently require Edit configuration. REST v1/OpenAPI covers managed database and bucket operations; dedicated CLI, Terraform and MCP database commands/resources are not provided. Existing generic API clients and the private tunnel CLI remain available.

Database backups reuse the operational backup policy and encrypted restic repository. PostgreSQL and MariaDB offer their supported native logical dumps; Redis and Valkey offer authenticated online RDB snapshots using the sealed managed password. Standalone managed MongoDB, MySQL and ClickHouse remain volume-backup only. Managed databases cannot restore in place. Separate recovery retains the exact deployed database descriptor and snapshot credentials, creates fresh storage and remains offline until explicitly deployed; older snapshots lacking typed metadata fail with guidance to redeploy on an updated worker and create a new backup. Public-TLS or pooler snapshots require the dedicated database maintenance recovery path rather than silently discarding their protection.

Canonical manifests preserve the database kind and safe metadata. Applying a redacted manifest to an existing database keeps its sealed credentials and dedicated settings. Creating a base database from a manifest generates fresh credentials; advanced pooler/extension/public-TLS configuration must first be created through dedicated settings and is refused if it cannot be reproduced. Portable exports always omit the database TLS private key. Resolved Compose maps use one decode/re-escape path across snapshot writers, including rollout generations, preserving literal dollars in keys, shell expressions and resolved secret values.

Directory integration uses the same permission catalogue for custom roles, managed membership claims and scoped tokens. Personal instance-administrator tokens with `directory:manage` may call the versioned directory settings APIs; every call rechecks current administration, second-factor enrollment, lockouts and the panel allowlist. SCIM `/scim/v2` is a separate instance credential class: API tokens and cookies do not authenticate it. Its OpenAPI operations advertise their own server and security scheme. LDAP uses verified LDAPS/StartTLS, pinned resolved addresses and the host's explicit `COVE_LDAP_ALLOWED_CIDRS`; it does not tunnel arbitrary LDAP through the HTTP proxy. GitHub directory HTTPS calls use the configured outbound transport. Prefixed installations retain the prefix in SCIM metadata and GitHub consent returns.

SCIM deactivation, deletion and identity changes that revoke credentials also delete scoped API tokens, deploy hooks and both owned deployment-status links and public uptime pages, suspend owned job schedules and request cancellation of their queued/running executions. Manual account disablement uses the same revocation. Local CLI context files remain on clients, but their revoked credentials no longer authenticate; MCP reauthenticates each request. Reactivating an account does not resurrect deleted tokens, links or suspended schedules. Saving a nonempty job schedule explicitly assigns the current account and requires both configuration editing and operation permission. Sharing assigns the current project editor on both public status surfaces; claiming a legacy uptime page or changing its creator rotates its slug. Both recheck the owner's current grants, account status, lockout and required second-factor enrollment; jobs recheck before dispatch too. Older links/schedules without reliable owner metadata fail closed until an authorised person explicitly rotates the link or saves the schedule. No historical owner is guessed from names or audit text. Cross-team resource transfers suspend owned schedules for an explicit destination-side save. Directory provisioning, deprovisioning, membership changes and failed synchronization enter the existing notification catalogue/queue; incident-only channels still require alert/recovery pairs.

### GPU assignment

Linux workers expose explicit, non-polling GPU inspection through administrator `GET /api/nodes/{id}/gpus` and resource-editor `GET /api/workloads/{id}/gpus`. Synthetic CDI Docker tests establish only inventory, selection, container edits and missing-device rejection.

## Deployed image vulnerability scans

Scanning requires both the node operator's `COVE_IMAGE_SCANNING=1` environment variable on the worker daemon and a team administrator's opt-in for that team/node pair. Restart the daemon after changing its environment, then verify the node. `GET/PUT /api/workloads/{id}/image-scanning` reads or changes that pair's `{enabled,notify}` settings; changes apply to all of the team's resources on that node. Disabling prevents new scans; cancel an existing operation separately. Settings default off. `POST /api/workloads/{id}/operations {"action":"image_scan"}` requires operator access and queues a serialized metadata operation, not a deployment. It reads retained service/job or managed database images without pulling application tags, waking resources, starting containers or changing Compose. Managed previews are excluded. Job schedule ticks blocked by scanning are retained.

The worker exports exact local image identities to a read-only archive, verifies the archive configuration against Trivy's report and runs the release-pinned scanner `docker.io/aquasec/trivy:0.76.2@sha256:8f6bb947dbc528902e11f2f5be52f7b519f6a39d5d148f41166f2040499768fb`. A Cove release changes this constant after local acceptance; every result records the pin, scanner version, database content hash/time and image identities. The scanner has no Docker socket, worker root, registry credentials or network, runs unprivileged with a read-only root and dropped capabilities, and has CPU/memory/process/time/scratch/output bounds. Telemetry, version checks, secret scanning and image-config scanners are disabled. Raw image configuration, descriptions, secret matches and arbitrary scanner JSON are not persisted; results retain bounded package/CVE identifiers, versions, severity counts and coverage. There is no deployment enforcement.

The main vulnerability DB is fetched anonymously from `ghcr.io/aquasecurity/trivy-db:2` in a separate bounded refresh container, with explicit repository selection, verified TLS, telemetry/version checks off, no Docker socket and no host credential configuration. Compressed download and extraction share a hard 2 GiB tmpfs; persistent active/staging generations total at most 4 GiB. Refresh is bounded to 10 minutes and 3 GiB RAM. Scans are limited to 16 distinct images, a 2 GiB archive/decompressed inspection budget, one CPU/2 GiB RAM per scanner, five minutes per image and twenty minutes per operation. Scanner report output is capped at 8 MiB, normalized operation results at 512 KiB, with at most 512 stored findings across the resource (256 per image). Counts remain available when findings are truncated. Missing, future-dated, expired or older-than-24-hour DB data produces unknown coverage, never a clean result.

Scanner requests carry only resource metadata and the panel-selected infrastructure proxy policy; application variables, database metadata, routes and registry credentials remain excluded. Proxy preparation is checkpointed before RPC so uncertain retries retain identical inputs. Database-refresh containers receive HTTP(S)/NO_PROXY through environment variables, while offline scan containers receive no proxy credentials. Acquiring a missing scanner image requires a matching Docker daemon proxy; cached offline inputs do not require a pull. Exact platform descriptors and exported configuration associations bind Docker 29 multi-platform identities; missing proof remains unknown. Moves and rollout decisions invalidate earlier result freshness.

**Java archive limitation:** this slice never downloads the Java index. JAR/WAR/EAR artifacts are detected in exported image layers and excluded from Trivy's Java archive analysis. Their Java dependency coverage is explicitly `not_scanned`/unknown beside OS and other-language findings, and the overall result remains unknown even when other findings are available. Detection is conservative across layers: an artifact removed in a later layer can still produce the limitation. No larger database-budget setting is provided. A separately bounded Java-index implementation is a possible follow-up.

`GET /api/workloads/{id}/image-scans` returns the latest terminal scan, effective coverage state and staleness after lifecycle attempts or DB expiry. Unknown/partial/stale reports must never be displayed as clean. A scan can complete as an operation yet report unknown coverage. Opt-in notifications use explicitly selected catalogue events (not By result or incident routing) and emit `image.vulnerabilities`, `image.scan_completed` or `image.scan_unknown`, with bounded CVE summaries and operation links. Turning notifications off suppresses pending delivery.

The opt-in native acceptance test is `COVE_TEST_SCANNER_DOCKER=1 go test ./internal/worker -run TestImageScanDocker -count=1`, only on an owned disposable Linux Docker daemon with the pinned scanner and Registry 2.8.3 fixture cached. `COVE_TEST_SCANNER_DATABASE_ARCHIVE` must name a fresh, bounded tar containing only `db/trivy.db` and `db/metadata.json`. It checks real offline findings, Java unknown coverage, secret-output exclusion and unchanged application containers. The packaged UI test is `python scripts/test-browser.py --image-scans e2e/image-scans.spec.ts`, with `COVE_BROWSER_SCANNER_DATABASE` naming that cached main database tar. The harness validates and seeds it before starting an opted-in worker; no public DB refresh is needed during browser acceptance. Keep the shared fixture lock and owner-checked cleanup enabled.

## Managed build registry

Team administrators can provision one active Cove-managed registry from Docker registries. `GET|POST /api/managed-registries` lists or creates the instance; creation selects a team-authorized ready node, project and exact DNS hostname. Workers must report both `managed_registry` and `file_secrets`. Initial deployment uses an HTTPS route with ACME; DNS and ingress reachability remain the operator's responsibility. A failed initial TLS verification can be repaired by uploading a certificate for that resource, saving `certificate_id` alongside retention, then retrying provisioning. The ordinary team registry connection is created only after the worker verifies authenticated HTTPS. Generated credentials remain sealed inside Cove and are never returned by these endpoints. Managed registries are infrastructure resources, are omitted from portable project declarations and cannot be cloned. Maintenance uses normal approval, freeze and deployment-window admission; authenticated verification honors the worker outbound policy.

The generated service uses native bcrypt authentication through a private file secret, no published backend port, a read-only root, dropped capabilities, one CPU, 512 MiB memory, bounded logs and its own labelled data volume. Its fixed release image is `docker.io/library/registry:3.1.2@sha256:82f6ff4a7f982960c8aa51617fea3aabc485df6e55cce80d22deb1de36f1bc3c`. Cove releases update `ManagedRegistryImage` after checking the official multi-platform artifact and rerunning local lifecycle acceptance. Generic resource mutations and ordinary connection Edit/Delete are blocked; use the registry's actions. The generated resource counts against team resource limits.

**No verified hard storage cap:** the supported local Docker volume has no verified filesystem quota. Retention and garbage collection are not a capacity boundary. API storage metadata explicitly returns `hard_cap_verified:false`; no storage-size input is offered. Verified quota-backed storage remains a prerequisite for adding hard registry caps.

Retention defaults to ten manifests per repository and thirty days minimum age. `PUT /api/managed-registries/{id}` saves explicit `retention` values (1-100 retained manifests, 1-3650 days). `POST .../{id}/gc` requests manual maintenance, not automatic scheduling. Admission refuses while team operations are active or the reference inventory is incomplete. The controller protects retained runtime releases/previews and the latest successful builds, and blocks new publishers/registry bindings during maintenance. Scheduled work remains due while this hold applies. Protected references are bounded to 4096. The stopped-volume inventory includes untagged revisions, verifies metadata digests, conservatively keeps foreign tags and unknown-age content, and protects retained image-index children. Age follows the newest local revision/tag publication time, not an image's supplied creation timestamp. Only eligible Cove-generated build tags can be retired. Unsupported, missing or oversized inventory fails closed.

Maintenance journals the original container identity, running state and restart policy before stopping it. The metadata helper and Distribution GC run with no network, no Docker socket, read-only roots, dropped capabilities and CPU/memory/process/time bounds; only the owned registry data is writable. Recovery removes only owned helper containers and confirms the registry's authenticated HTTP health check before releasing maintenance. Lost submissions are retired by an idempotent cancellation journal so a late delivery cannot execute after the controller releases the hold. Cancellation can leave some eligible data already deleted; it is not rollback. Failed recovery remains pending and prevents publishing until the worker settles it.

`POST .../{id}/retry` retries failed provisioning. `DELETE .../{id}` takes `{delete_data:false}` by default, stops/removes the registry service and route and removes its generated connection, while retaining its labelled data volume and read-only resource history. Disconnect resources and registry webhooks first. Explicit `{delete_data:true}` requires no protected references and permanently purges the owned volume; a retained removed instance can be purged later. Failed removal restores its prior state rather than inventing a ready instance. Removing the registry makes its images unavailable for new pulls even when their data was retained; existing application containers are not restarted.

After data is purged and operations have settled, `DELETE .../{id}/record` with no body explicitly deletes the empty registry resource and its operation history. It confirms worker cleanup before releasing node, project and resource-quota references. This action cannot be undone; it does not delete running applications or image data a second time.

Native tests require an owned disposable Linux Docker daemon with the exact pinned registry, cached Traefik and BusyBox fixtures. `COVE_TEST_MANAGED_REGISTRY_DOCKER=1 go test ./internal/worker -run '^TestManagedRegistryDocker$' -count=1` covers real authenticated push, immutable pull/deploy, retention/GC, cancellation, lost-ack recovery and removal. The matching control test additionally needs an owned test PostgreSQL URL and `COVE_TEST_WORKER_BINARY` naming the compiled local worker. Packaged UI acceptance is `python scripts/test-browser.py --managed-registry e2e/managed-registry.spec.ts`; its caller must supply `COVE_BROWSER_MANAGED_DAEMON_ID` matching its verified owned nested daemon. Fixture-only CA trust and DNS entries are scoped to the generated hostname and removed with ownership checks before the shared browser lock is released. No real DNS or certificate provider is used.
